# tilefish

A typed tensor language for GPU inference. The shape, dtype, layout and
quantization format of every tensor live in its type, operators come from a
typed library, and a model is built once into GPU binaries plus a manifest.
Thin Python, C++ and Rust hosts are generated from the same signatures.

**Status: early preview (0.0.3 on PyPI, 0.0.1 on crates.io).** The Python package type-checks:
tensor types and block-scaled formats, the four declarations below, tracing
into a typed IR, and Triton ahead-of-time compile specs for `extern` kernels,
in pure Python with no dependencies. A `@kernel` also lowers to Triton
source, as a row kernel or an elementwise kernel (`tilefish.lower`), with its
numerics contract written down in the module.
With the `gpu` extra (`pip install "tilefish[gpu]"`: torch, Triton,
cuda-python) a compile spec builds into a cubin (`tilefish.aot.build`, with a
manifest and a digest of the machine code) and a kernel runs from Python in
the three modes below (`tilefish.run`). A Rust host (the `tilefish` crate,
`crates/tilefish`) loads a manifest directory and launches its cubins, with typed
launchers generated by `tilefish.hosts.rust.emit`; there is no C++ host, and
the `tilefish build` command is still the plan.

## Why

In inference code the contract of a kernel is usually written three times and
checked by none of them:

- the shape, dtype, alignment and aliasing rules sit in a docstring, a few
  `assert`s and a comment above a C ABI;
- a block-scaled weight format (MXFP8, MXFP4, NVFP4) is described in prose,
  together with the per-architecture byte layout of its scales;
- the same kernel is ported by hand from Triton to CUDA C++ to Rust, and parity
  tests chase the last ULP (FMA contraction, flush-to-zero, reduction order)
  after the fact;
- which implementation runs at which `(M, N, K)` on which GPU is a table
  someone measured once.

tilefish moves all of that into types, so the compiler can check it, generate
it and reason about it.

## What it looks like

```python
import tilefish
from tilefish import Dim, Tensor, InOut, Out, BlockScaled, const
from tilefish import bf16, f32, e4m3, e2m1, ue8m0

M = Dim("M")                          # runtime dimension
D = Dim("D", 2560)                    # static: baked into the binary
H = Dim("H", 1024)
F = Dim("F", 3072)
K = Dim("K", divisible_by=32)         # constraint, checked at build time
N = Dim("N", divisible_by=128)

mxfp8 = BlockScaled(elem=e4m3, scale=ue8m0, block=32, axis=-1)
mxfp4 = BlockScaled(elem=e2m1, scale=ue8m0, block=32, axis=-1)
nvfp4 = BlockScaled(elem=e2m1, scale=e4m3, block=16, global_scale=f32)

# A kernel whose body tilefish understands: it can be fused, and it is
# lowered to Triton.
@tilefish.kernel
def residual_add_rmsnorm(
    x: Tensor[M, D, bf16],
    residual: InOut[Tensor[M, D, f32]],
    w: Tensor[D, bf16],
    *, eps: const[f32] = 1e-6,
) -> Tensor[M, D, bf16]:
    r = residual + x.to(f32)
    residual[...] = r
    rstd = tilefish.rsqrt(tilefish.mean(r * r, axis=-1, keepdims=True) + eps)
    return (r * rstd * w.to(f32)).to(bf16)      # the only rounding point

# An existing hand-written kernel, unchanged, given a type.
n = Dim("n", divisible_by=16)

# (index_bits=32 is the default: a kernel that offsets with i32 gets a max_elements
# limit of 2**31 - 1 on every tensor, which both hosts check; a kernel that
# indexes in i64 says index_bits=64.)
@tilefish.extern(triton=my_kernels.gelu, num_warps=4,
                 grid=lambda n: (tilefish.cdiv(n, 1024),))
def gelu(x: Tensor[n, bf16], y: Out[Tensor[n, bf16]],
         n_elem: n, BLOCK: const = 1024): ...

# A library operator: opaque body, typed signature, pluggable epilogue.
@tilefish.library("gemm", acc=f32)
def gemm(a: Tensor[M, K, bf16], b: Tensor[N, K, mxfp8]) -> Tensor[M, N, bf16]: ...

# A model is ordinary Python over typed values.
@tilefish.graph
def mlp(x: Tensor[M, H, bf16], w_gu: Tensor[2 * F, H, mxfp8], w_d: Tensor[H, F, mxfp8]):
    g, u = gemm(x, w_gu).split(F, axis=-1)
    a = (tilefish.silu(g.to(f32)) * u.to(f32)).to(bf16)
    return gemm(a, w_d)
```

## How a build works

```sh
tilefish build --arch sm_90,sm_100,sm_120 --host python,rust,cpp
```

1. Trace the graph into a typed IR and check it: shapes, dtypes, divisibility,
   aliasing, and which architectures each operator supports.
2. Run the rewrite rules (below) and settle the final list of kernels.
3. Lower each `@kernel` to Triton source, written to disk for review.
4. Derive Triton's compile inputs from the types: pointer dtypes and 16-byte
   alignment, `constexpr` values from static dimensions, divisibility hints
   from `divisible_by`, and one binary per bucket for bucketed dimensions.
   Compile ahead of time to one cubin per architecture.
5. Write a manifest: symbol, parameter ABI in order, grid rule, block size,
   shared memory, launch attributes, toolchain versions, and a digest of the
   machine code.
6. Generate the hosts from the manifest and the types: a `torch.library`
   custom op for Python, a header for C++, a `cudarc` crate for Rust. Every
   precondition that selected a binary (alignment, divisibility, static sizes)
   becomes a check in the generated launcher, so no host can run a binary
   under assumptions it was not compiled for.

Library operators put a different code object behind the same kind of
manifest entry: a CUTLASS instantiation with a C entry point, a CuTe DSL
ahead-of-time export, or a pinned cuBLASLt algorithm recorded with its
workspace size and replayed as is (the last exists: a bf16 GEMM, below).

The Python side has three modes:

| mode | what runs | used for |
|---|---|---|
| `jit` | the current source, built through its compile spec (the path of the build) in memory and launched through the CUDA driver | iterating on a kernel |
| `reference` | the same bodies interpreted with torch | an oracle, compared within a tolerance |
| `replay` | the prebuilt cubins of a manifest directory, checked against its digests, through the CUDA driver; it needs a trust anchor, the manifest's pinned digest or an explicit `trust_directory=True` | the exact machine code the C++ and Rust hosts run |

```python
y = tilefish.run(residual_add_rmsnorm, x, residual, w)                        # jit
m = tilefish.runtime.export(residual_add_rmsnorm, "build/")                    # cubins and manifest.json
y = tilefish.run(residual_add_rmsnorm, x, residual, w, mode="replay", manifest="build/", pin=m.digest)           # a manifest whose digest you hold
y = tilefish.run(residual_add_rmsnorm, x, residual, w, mode="replay", manifest="build/", trust_directory=True)  # whatever the directory holds
```

`replay` refuses to run without one of the two (`pin=` or `trust_directory=True`). This
is a deliberate breaking change in 0.0.x: until 0.0.2 a replay trusted the directory by
default, and the digests in it sit next to the files they describe, so whoever can write
the directory could make it run any binary.

A pin is of one exported artifact, not of a recipe. The manifest digest covers the cubin
files, and a cubin's debug sections name the directory it was built in. Exporting the
same graph again, elsewhere or after a build-cache hit, can therefore give another digest
for the same machine code: every binary's `sha256_code`, the pinned GEMMs and the plan
are unchanged. Pin what you exported, and ship that directory.

Arguments are torch tensors, matched to the signature the way a call is
matched in a trace: inputs and `InOut` tensors are passed (an `InOut` tensor
is updated in place), `Out` tensors are allocated and returned. Before a
launch every precondition of the binary is checked (dtypes, static sizes,
`divisible_by`, 16-byte aligned pointers, contiguity), and a bucketed
dimension must equal a bucket exactly: there is no padding.

`jit` and `replay` launch the same way, so they run the same machine code: a
cubin that `jit` builds has the `sha256_code` of the one in the manifest.
`replay` refuses a cubin whose digests are not the manifest's, a manifest
entry that is not what the operator's compile spec asks for, and a stale
binary: a kernel redeclared with another body but the same name and signature
does not replay its old binary.

**What a binary is, is the Triton IR its kernel compiles to.** Which kernel
Triton compiles depends on everything the Python process holds when its
frontend runs: the text of the function and of the jit functions it calls, the
module constants it reads (`cfg.SCALE`, `getattr(cfg, "SCALE")`, `getattr(cfg,
"SC" + "ALE")`, a class attribute `cfg.Inner.SCALE`), closure variables, a
`triton.constexpr_function` that reads the environment, a `tl.constexpr` of an
object whose `repr` hides its state, a helper two modules away, a user module
named like a standard library module. Five rounds of review found a route that
each way of *looking for* these (a digest of the files a kernel reaches, the
module attributes, the closures, a watch on the imports) did not follow, and each
was a stale binary served by the build cache or by an export replayed with a
pin. So nothing is looked for. Triton's frontend folds every one of them into
the IR it builds, and that IR is hashed (`tilefish._ir`): the TTIR that
`ASTSource.make_ir` builds, printed with `Module.str_nodebug()` (no locations,
no names of values). Where the kernel is (its path, its line numbers), comments,
blank lines and the names of local variables are not in it, so none of them is an
edit; the operations, the types, the constants and the functions that are called
are. Whatever the process holds is what is hashed, because that is what is
compiled. The digest of every build is in `BuiltKernel.ir_digest`, and in the
manifest entry as `source_digest` with `source_digest_kind` `"tilefish.triton-ir.v1"`
(the fields schema 2 already had, so a reader of the manifest reads it as before;
a lowered kernel has its `source_sha256` as well, which needs no Triton).
`replay` recomputes the digest from the kernel the process holds, when Triton
can be imported and is the version that built the entry, and refuses a mismatch
as stale, with a pin or not (without Triton, or with another version, whose IR
may print differently, only a pin vouches for a hand-written kernel; the versions
are compared first, so a Triton whose frontend differs is never asked to run it).
The frontend costs 2 to 8 ms per kernel on a B300 (no compile, no GPU), once for
each build, `jit` call and `replay` call. It runs under the same lock as a
compile, so no two frontends, a compile's own included, run at once in any threads.

So an edit that was not reloaded is not a special case. `export` in the process
that imported the module compiles, and stamps, what that process holds; a fresh
process with the edited file computes another digest and refuses the manifest.
Triton's own `cache_key` is not used, and a build never reads Triton's disk
cache. What was removed: the digest of the files a kernel reaches, the import
watch (`SourceFileLoader.exec_module` is not wrapped and `TILEFISH_IMPORT_WATCH`
is gone), the snapshot of module attributes and the refusal of a reassigned one
(a value that a program assigned is in the IR), and the walk over the values
and closures of a kernel with its refusal of a value that has no stable `repr`.
What stays: the check, for a *lowered* kernel, that its module file has the
`source_sha256` of its spec and that the function the process holds was
imported from those lines (the IR digest says what the process holds, not that it
is the source the spec claims); that `build(spec, fn=)` compiles the function
the spec names and no other; and the refusal of whatever makes Triton compile
something other than the IR: its kernel override (`TRITON_KERNEL_OVERRIDE`) and
the compile option `ir_override` replace the IR of a stage with a file (so the
binary would not be of the IR), and an active instrumentation plugin
(`CUDABackend.instrumentation`) patches the passes.

A build compiles from scratch (25 to 120 ms per binary on a B300) unless
tilefish's own cache has it: `~/.cache/tilefish`, or `$TILEFISH_CACHE_DIR` (an
empty value switches it off; `aot.build(..., cache=False)` skips it for one
build). Its key is the cache recipe (a number that is bumped whenever tilefish
changes what goes into a binary) and the tilefish version, the IR digest, the
compile options, the architecture, the Triton and `ptxas` versions, and the
Triton settings that change code generation: every environment variable of the
families `TRITON_`, `MLIR_`, `LLVM_`, `NVPTX_`, `AMDGCN_`, `DISABLE_`, `ENABLE_`,
`ALLOW_` and `USE_IR_LOC` except those known not to (cache and dump directories,
tool paths, debugging switches), which is more than the 30 that Triton lists as
cache-invalidating (it leaves out `TRITON_LIBDEVICE_PATH`,
`TRITON_MOCK_PTX_VERSION` and `TRITON_KERNEL_OVERRIDE`, among others), the
effective value of each codegen knob of `triton.knobs` and the sha256 of the
libdevice file when a path is set. A setting that names a file Triton reads is
keyed by the sha256 of the file, not by its path, so a file rewritten under its name
is another binary: the compile option `extern_libs`, `TRITON_LIBDEVICE_PATH` and
`LLVM_PASS_PLUGIN_PATH` (a file that cannot be read refuses the build); the rest
of what Triton 3.5.1 has that names a path is a tool (`ptxas`, whose version is in
the key), an output, or the launcher's, and `_cache.py` lists it. Every read is verified: the `sha256` and
`sha256_code` of the cubin are recomputed (and the PTX, the entry point and its
ABI, the options, the IR digest and the versions are checked), and an entry that
is not as it was written is a warning and a rebuild, never used, and a cache
that cannot be read or written never fails a build, also under `python -W error`
(the warning is then logged on `tilefish.cache` instead of raised). Entries are
written through a temporary file and renamed, so builds that race do not tear
one. A lookup is a run of the frontend and a read: 3 to 6 ms. Nothing evicts the
cache, it is no defence against someone who can write the directory (a manifest
is what to pin), and it tells a patched Triton that keeps its version string from
the original no better than the version does.

`replay` also refuses `shared` memory the cubin and the device cannot have (the
driver's static shared memory of the function plus the manifest's dynamic size
must fit the device's opt-in maximum), an argument list that does not fit the
ABI, and a grid beyond the device's limits. The manifest is read as strict JSON
(no duplicate keys, no `NaN`, no number that does not fit a float), files are
written through a temporary file and renamed, and a symbolic link where a file
is to go is refused.

**Trust.** A replay needs a trust anchor, `pin=` or `trust_directory=True`, and
raises without one. The digests in a manifest directory sit next to the files
they describe, so whoever can write the directory can rewrite both.
`export` returns the manifest with its `digest`, a sha256 over every entry, and
checks that the directory it wrote has that digest; keep it somewhere you trust
and pass it as `pin=` to refuse a directory that changed.
`trust_directory=True` is the explicit statement that whatever the directory
holds is fine (a directory you wrote a moment ago); it does not combine with
`pin=`. A pin vouches for the manifest, not for an IR digest that is known to
differ, and not for a `shared` that is nonzero but too small for the kernel
(nothing but the manifest says how much it needs). Triton's own JIT launcher,
which specializes on argument values, is not a mode. Neither `jit` nor `replay`
needs a C compiler, and a `replay` of a generated kernel needs neither Triton nor
`ptxas`.

CI asserts, on a GPU (the tests marked `gpu`), that a `jit`-built cubin has the
digest of the manifest's, that `jit` and `replay` agree byte for byte, and that
`replay` stays within tolerance of `reference`. The tolerances are measured per
input distribution and tabulated in `python/tests/test_gpu_reference.py`: a ULP
count only means something where the result is far from zero (a layernorm of
data with a large mean has tiny outputs), so a bf16 output is bounded by half a
bf16 step of the largest reference value and a fraction of elements that may
differ, the f32 softmax by an absolute error of 5e-7, the gelu by 3e-5. An
experiment that passes in `replay` is, kernel for kernel, what production runs.

## Views, device scalars, prebuilt binaries and a pinned GEMM

A real model needs four things that a dense, compiled-in, Triton-only operator cannot say. Each is part of the manifest, which is schema 3
(`docs/manifest-schema-3.md` specifies every field; the Python package reads and writes only schema 3, and says "re-export" for schema 2).

**Strided views.** A tensor type has element strides and an element offset, in the dimension algebra (`TensorType.strides`, `.offset`); dense
and 16-byte aligned (`contiguous`) is the default. `x.reshape(M, 3, H, D)` (a dense input), `x.permute(1, 0, 2)`, `x[:, 1]` / `x.select(axis, i)` and
`x.split(...)` copy nothing: they are views with the strides and the offset of the operation. A view is a `View[...]` and can go into traced
elementwise and reduction ops; a declared operator takes one only where its parameter says so. Every other tensor parameter (and result) of a kernel,
extern, library op or graph is contiguous: an annotation that is a `TensorType` with other strides, an offset or no alignment is refused at the
declaration, and a launch refuses a tensor that is not contiguous for such a parameter. An `extern` parameter `x: Strided[Tensor[S, H, D, bf16]]`
takes a view, and the kernel's strides are scalar parameters the stub declares in the kernel's argument order:

```python
@tilefish.extern(triton=head_copy, grid=lambda S: (S, 8))
def head_copy(x: Strided[Tensor[S, 8, 64, bf16]], y: Out[Tensor[S, 8, 64, bf16]],
              x_s0: StrideOf("x", 0), x_s1: StrideOf("x", 1), D: const = 64): ...      # the last axis has stride 1

y = tilefish.run(head_copy, qkv[:, 1])        # a view of a fused qkv tensor: its pointer and its two strides go to the kernel
```

An axis without a `StrideOf` must be the last one (its stride is then 1, and a view that does not have it is refused); the strides are bound at a
call like shapes are, range-checked as `i32` (`i64` for `index_bits=64`), and a strided pointer is bounded by its extent (`max_extent`), not its element
count. The pointer passed is `base + offset * itemsize`. `Strided[Tensor[...], 16]` compiles the kernel for a 16-byte aligned pointer
(`tt.divisibility=16`), which the offset must then provably allow (a trace call refuses an offset that is not a multiple of 16 bytes, a launch
checks the address); without the `16` Triton gets no hint and any element-aligned view runs. Lowered `@kernel`s still take contiguous tensors only: a
view in a kernel body is refused with the rule that says so.

**Device scalars.** `n_tok: DevScalar[i32]` is one element in device memory: in the ABI a pointer with the shape `[]`, at the API a tensor of one
element. A binary reads it with `tl.load`, so one binary serves every value and a value changes by writing memory, never by building; a lowered kernel
reads it with `tilefish.load(s)` (one `tl.load(ptr)`, broadcast).

**Prebuilt binaries.** `@tilefish.extern(ptx="k.ptx", symbol="k", block=(256,), grid=...)` or `cubin={"sm_103": "k.cubin"}` declares a kernel that
Triton does not compile, by its C ABI: pointers, `Dim` scalars and typed `const[i32|i64|f32]` fixed arguments, in order, and **no Triton scratch slots**.
Its identity is the sha256 of the bytes of the file (`source_digest` of kind `tilefish.binary.v1`); PTX is assembled by `ptxas` with fixed, recorded flags
(the ones Triton passes, so the PTX of a Triton build declared this way gives the machine code, and the output bytes, of the Triton path); a cubin is used
as it is for its own architecture and refused for another. `replay` refuses a file that is not the one the manifest was built from.

**A pinned cuBLASLt GEMM.** `@tilefish.library("gemm", acc=f32, impl="cublaslt.gemm")` over `(a: Tensor[M, K, bf16], b: Tensor[N, K, bf16]) ->
Tensor[M, N, bf16]` computes `a @ b.T` with an f32 accumulator and one rounding (`impl="cublaslt.gemm_bias"` adds `bias: Tensor[N, bf16]`, added in f32 before it).
For each `(M, N, K, bias)` (`M` from its buckets) the algorithm that cuBLASLt's heuristic ranks first under a fixed workspace limit (8 519 680 bytes,
torch's default; `workspace_bytes=` changes it) is pinned: its 64 bytes go to the manifest's `library` section with the cuBLASLt version that chose
it and the SM count of the device it chose it on (`sm_count`: a MIG slice has fewer SMs than the whole GPU), and `replay` runs that algorithm and refuses
another cuBLASLt version and a device of another SM count ("re-export the manifest on this device"). `jit` pins in memory the same way, per device, so
`jit` and `replay` run the same algorithm. The binding is ctypes on the `libcublasLt` the process already has loaded (torch's); operands are contiguous and 16-byte aligned (strided
operands are not supported yet).

## Launch plans: a graph as a static list of launches over one arena

A model forward is not one kernel. `tilefish.plan(graph, buckets=...)` compiles a `@tilefish.graph` into a **launch plan**: for every combination of the bucket values of its
dimensions, the ordered launches of manifest entries (a lowered kernel, a hand-written Triton extern, a prebuilt binary or a pinned cuBLASLt GEMM), with every pointer argument bound to a
buffer or to a *view* of one (a `reshape`, `permute`, `select` or `split` copies nothing), and **one arena of device memory** for everything the caller does not provide: the intermediates, one
slot per `DevScalar` input and the cuBLASLt workspace. Every arena buffer has a fixed byte offset, a multiple of 256, **the same in every bucket** (the arena is sized for the largest), so a plan
can be captured in a CUDA graph once per bucket at fixed addresses. The steps run on one stream in the order of the IR, with no synchronization between them and none implied (an in-place call
keeps the storage of the version it consumes). `reuse=True` lets intermediates share bytes where no step uses both: the transformer block of the gate (rmsnorm, a bias GEMM whose output is split
into q, k and v views, an attention that masks the keys at a device scalar `n`, a GEMM, a residual add and rmsnorm, two GEMMs around a gelu, a residual add; rows bucketed over 32, 64 and 128)
needs 9 634 048 bytes without reuse (8 519 680 of them the workspace) and 9 240 832 with it; unrolled 24 times (216 launches per bucket, the weights of the layers views of stacked
parameters) the arena is 36 765 952 bytes without reuse and 9 306 368 with it, one layer's intermediates plus the workspace whatever the depth.

```python
plan = tilefish.plan(block, buckets={"M": [32, 64, 128]}, reuse=False)       # no GPU, no torch: steps, buffers, offsets
p = tilefish.runtime.export(block, "build/")                                  # binaries, manifest.json and plan.json (schema "tilefish.plan.v1"); p.digest is the pin
y = tilefish.run(block, x, n, *weights)                                       # jit: the same plan, binaries built in memory
y = tilefish.run(block, x, n, *weights, mode="replay", plan="build/", pin=p.digest)   # a verified plan directory, or trust_directory=True
y = tilefish.run(block, x, n, *weights, mode="reference")                     # each op's reference composed in torch
cap = tilefish.capture(block, x, *weights, devscalars={"n": n}, outputs=y)    # the plan in a CUDA graph of its own
cap.set_devscalar("n", 17); cap.replay()                                      # a replay ordered with every run of the plan, from any thread
```

`plan.json` carries the plan and the digest of the manifest it was built against, so **pinning the plan digest pins every binary and every pinned GEMM algorithm it launches**. A replay loads and
verifies the file and its manifest (a tampered plan, a wrong pin, a plan built against another manifest, and a plan of a graph that changed are all refused), allocates the arena once per device
and keeps it, and checks **every step's preconditions before the first launch**: a failure launches nothing, not even the write of a device scalar. A run allocates nothing but its outputs
(`outputs=` gives them) and waits for nothing: the GEMM workspace is in the arena, a device scalar is written by a stream-ordered copy. So **a replay under `torch.cuda.graph` captures and the
graph replays byte-identically** (`runtime.prepare` does the allocating and the loading that cannot happen inside a capture; `docs/plan-schema-1.md` lists every reason a plan could fail to
capture). Every run of a plan on a device uses the one arena, so **runs of one plan on several streams (or threads) are ordered on the device** by an event of the arena: a run waits on its
stream for the run before it and records the event after its last launch, so they never overlap and their results are correct, at the cost of running one after the other.
`tilefish.capture(graph, *inputs, devscalars=..., outputs=...)` captures the plan in a CUDA graph of its own: its `replay()` takes the arena's lock and waits for and records that event
around the graph, as a run does, so **its replays are ordered with every run and replay of the plan, from any thread and on any stream**, and `set_devscalar` changes a device scalar for
the next replays with no synchronization. A plan run inside your own `torch.cuda.graph(...)` captures too: the wait and the record are external event nodes of the graph, so its arena is
the plan's arena and its replays are ordered with the runs whose record they see. But torch's `replay()` takes no lock: **a raw graph replayed while another thread is in the middle of a run
of the same plan overlaps that run** (wrong bytes, no error), so order the two yourself or use `tilefish.capture`. `jit` and `replay` are one code path over binaries from two places, so they are identical by construction, and the gate checks on a GPU that plan replay, plan jit and the per-op
eager composition of the same ops give the same bytes for every bucket and two values of `n`.

A plan launches declared operators and views. Arithmetic traced in the graph body, a `store`, an `Out` parameter, a call to another graph, an in-place call on a view and a view read after its
tensor was updated in place are refused with the rule that says so; there is no fusion in a plan yet. `docs/plan-schema-1.md` specifies the file exactly (every field, the validation rules, the
digest) for the host that will run it without Python.

## The Rust host

The `tilefish` crate (`crates/tilefish`, version 0.0.1) is the
host of a manifest directory, without Python or Triton: it reads the manifest as
strict JSON, recomputes the digests exactly as Python does (the `sha256` of each
cubin, the `sha256_code` of its machine code, and the digest of the whole
manifest) and refuses a directory whose digest is not the pin it is given
(`Pin::Digest`; `Pin::TrustDirectory` is explicit). It builds on cudarc's safe
layer and calls the driver directly nowhere: `Manifest::kernel(&ctx, ...)` loads a
cubin into a `CudaContext` that the kernel then keeps alive, and the kernel
launches on a cudarc `CudaStream` (`Kernel::launch`, safe: the stream is checked
to be of the kernel's context) or, with the `unsafe` `Kernel::launch_raw`, on a
raw `CUstream` (it makes the kernel's context current for the call and puts back
what was). A tensor is made of a cudarc `CudaSlice` or view (`from_cuda`: no
`unsafe`; it borrows the slice, so the slice cannot be freed under it, and making
it records nothing on the slice) or of a region the host vouches for (`unsafe
DevicePtr::from_raw`, which has a lifetime and no tracking). The launch gives a
slice to cudarc's launch builder on the stream it launches on, which orders it
after the slice's earlier writes, and makes the slice's own stream wait for the
kernel, so freeing the slice (or any later work on its stream) runs after the
kernel however many other streams read it; a kernel that writes a slice from
another stream first waits for everything enqueued on the slice's own stream, so
it runs after all earlier readers. (A reader after a writer on another stream is
cudarc's own tracking, which needs a context that has made a stream of its own;
an `Err` from a launch does not promise that nothing was launched, and the crate
orders the free behind a kernel that may have run.) A CUDA graph is captured
with `launch_raw` (or `launch`) and regions: the graph holds the addresses and
nothing that keeps the memory alive, so it must not be replayed after the memory
is gone, and a launch of slices on a capturing stream is an error, not a graph,
whatever the cudarc context. The loaded function's parameter sizes are compared
with the ABI of the manifest (`cuFuncGetParamInfo`, as Python's `replay` does), and
a cubin whose ELF header names another architecture than its entry is refused.
`cudarc` panics when there is no NVIDIA driver, so `tilefish::driver_available()`
says first.

A manifest (schema 3) carries what a host needs to check a launch on its own:
every pointer parameter records its declared shape, with static axes as sizes
(`["Rows", 1024]`), and every entry the constraints of its named dimensions
(`divisible_by`, `buckets`, and the bucket the binary is built for). A launch
takes nothing but its tensors. The crate binds the dimensions from their sizes
(and the stride dimensions of a strided view from its canonical strides),
checks that they agree across arguments and with the static sizes, the exact
bucket and `divisible_by`, the dtype and rank of each tensor (a device scalar is
one element), `max_elements` and, for a view, `max_extent`, that the runtime
scalars (derived from the dimensions, from the element count of the tensor they
count, or from a stride) fit the 32 or 64 bits they are passed as, aliasing, the
alignment each pointer promises (16 bytes, or a strided pointer's element size),
contiguity of a tensor given for a parameter that is not strided, and the grid
against the device's limits, and evaluates the grid from its expression. There is
no way to tell a launch what a dimension is. A manifest of an older schema is
refused by both hosts: export it again.

**Schema 3 and the crate.** The crate reads manifest schema 3
(`docs/manifest-schema-3.md`) in full and launches everything it describes:
Triton kernels and prebuilt PTX and cubin binaries (exactly their parameters, no
scratch slots, `fixed` arguments at their slots), strided views
(`TensorRef::from_cuda_strided`, or over a region with `new_strided`; any element
strides and any offset), device scalars (a tensor of shape `[]` or `[1]`), `i64`
strides, and the pinned cuBLASLt GEMMs of the `library` section
(`Manifest::gemm`, `Gemm::launch`, and `unsafe Gemm::launch_raw` for a CUDA
graph). A GEMM runs the 64-byte algorithm the manifest pinned through cudarc's
`cublaslt::result`: it is refused when the process has another cuBLASLt than the
one that chose it, when the algorithm is not one cuBLASLt would have produced,
and when the library does not approve it for the problem. Its workspace is the
caller's last tensor (`Gemm::alloc_workspace` allocates the size the entry says),
so a launch allocates nothing and can be captured; the slices of a GEMM are
ordered like a kernel's. The published crate 0.0.1 reads schema 2 only. `emit`
writes typed launchers for all of it; the committed fixtures of the crate are
schema 3 manifests.

```python
from tilefish.hosts import rust
rust.emit(m, "launchers.rs")   # m = tilefish.runtime.export(...); ops=[...] cross-checks the declarations
rust.emit("build/", "launchers.rs", pin=m.digest)   # a directory is read only with its pin
```

`emit` takes a pinned manifest (the one `export` returns, `Manifest.load(path, pin=...)`,
or a directory with `pin=`: the file it writes is compiled and run, so a manifest
nobody vouched for does not write it, and every field that reaches it is
validated) and writes one Rust module with a struct per binary (per bucket), whose
`launch` takes typed tensors (`TensorRef<'a, Bf16>`, `TensorMut<'a, F32>`: the
borrow of a cudarc slice, or a region of device memory with its length that the
host vouches for with `unsafe DevicePtr::from_raw`; a shape that needs more bytes
than the memory has is refused, and so is a launch on a stream of another context
or of a tensor of another context) and documents the binary: its tensors, its
dimensions and their constraints, what is compiled in. It also embeds the digest
of the manifest it was generated from and refuses any other, and with
`embed=True` the manifest and the cubins as well. The output is deterministic.
`ops=` is optional: each declaration it lists must be exactly what the manifest's
entry says, and gives the docs the tilefish signature.

The byte-identity gate (`python/tests/rust_gate.py` with
`crates/tilefish/tests/gpu_gate.rs`) checks on a GPU that the Rust host and
`replay` agree byte for byte, on a fresh export and with the manifest directory
and with the embedded manifest, for the five goldens, a bucketed row kernel over
each bucket, the hand-written kernels (outputs and in-place tensors), a `tl.dot`
kernel that needs more than 48 KiB of dynamic shared memory, strided views
(a fused qkv, any element offset, aligned and not, transposed and expanded
views, 64-bit strides), device scalars, prebuilt PTX and cubin binaries (the PTX
of a Triton build and hand-written PTX with `fixed` arguments) and the pinned
cuBLASLt GEMMs with and without a bias at every bucket; it also checks the
refusals of schema 3, a strided kernel and a GEMM captured in a CUDA graph, and
the order of the frees of their slices against other streams. On any machine,
`cargo test` and `pytest` check that the digests Rust computes from a committed
manifest directory (`sm_103`, and a cross-compiled `sm_120` one) are the ones
Python computes, that Rust decides the same as Python on a thousand calls, and
that Rust refuses what Python refuses.

## Rewrites that know about rounding

Types make fusion legality mechanical: elementwise chains into GEMM
epilogues, a norm into the preceding residual add, quantization into the next
GEMM's prologue, permutations into strides instead of copy kernels, in-place
reuse of buffers. Bytes and FLOPs per operator follow from shapes and dtype
widths, so a build can report a roofline per kernel and count launches per
step.

Fusion can also change numerics. Every cast to a narrower type is a rounding
point in the IR, and rules come in two kinds:

- **exact**: every rounding point is kept and only kernel boundaries move.
  Applied automatically.
- **numerics-changing**: a reduction order, an accumulator dtype or a rounding
  point changes. Applied only on request, and gated against the reference.

`num_warps` is part of a kernel's numerics identity in the same way: it fixes
the tree a `tl.sum` adds in, so the same kernel with another warp count differs
in the last bits. It is recorded in the declaration digest, the compile spec
and the manifest, and a replay refuses an entry that has another.

Whether a legal fusion is worth doing is still measured, not assumed. The
measurements live in the repository next to the rules.

## What tilefish is not

- **Not a kernel compiler.** Triton, CuTe DSL, cuTile, Helion and TileLang
  write kernels. tilefish types them, builds them and hosts them.
- **Not a serving runtime.** Scheduling, KV cache, batching and request
  handling stay in the host program. tilefish owns one forward step over
  buffers it has planned.
- **Not a promise to generate every kernel.** Hand-tuned attention and GEMMs
  enter as `extern` or library operators and keep their own numerics
  contract.

## Roadmap

- **V0: one real model, end to end.** The whole GPU forward of a production
  model of about 0.6B parameters (a convolutional front end, a bidirectional
  encoder and a causal GQA decoder) is written in tilefish. The generated Rust
  host replaces the hand-written launch code of an existing engine and
  reproduces its output byte for byte on every architecture it ships for.
  Starting from a naive version of the model, the rewrite rules rediscover the
  fusions that were made by hand. V0 needs typed signatures and manifests,
  `extern` for Triton functions and prebuilt PTX or cubins, strided views,
  device-side scalars, gather / scatter / im2col style index kernels, a static
  launch and memory plan per shape bucket, pinned GEMMs, and a numerics
  contract on every operator.
- **V1: quantization as types.** MXFP8, MXFP4 and NVFP4, with generated
  quantize and dequantize references and per-architecture scale layouts.
- **V2: more of the forward generated.** Row reductions and elementwise
  families lowered natively, and GEMM epilogue fusion through CUTLASS or
  CuTe DSL.
- **V3: C++ and Rust as first-class deploy targets**, with the Python
  frontend used only at build time.
