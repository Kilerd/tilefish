# tilefish

A typed tensor language for GPU inference. The shape, dtype, layout and
quantization format of every tensor live in its type, operators come from a
typed library, and a model is built once into GPU binaries plus a manifest.
Thin Python, C++ and Rust hosts are generated from the same signatures.

**Status: early preview (0.0.8 on PyPI, 0.0.6 on crates.io; the C++ host builds from this repository).** The Python package type-checks:
tensor types and block-scaled formats, the four declarations below, tracing
into a typed IR, and Triton ahead-of-time compile specs for `extern` kernels,
in pure Python with no dependencies. A `@kernel` also lowers to Triton
source, as a row kernel or an elementwise kernel (`tilefish.lower`), with its
numerics contract written down in the module.
With the `gpu` extra (`pip install "tilefish[gpu]"`: torch, Triton,
cuda-python) a compile spec builds into a cubin (`tilefish.aot.build`, with a
manifest and a digest of the machine code) and a kernel runs from Python in
the three modes below (`tilefish.run`). The manifest (schema 3) also takes
strided views, device scalars, prebuilt binaries and pinned cuBLASLt GEMMs,
and a `@tilefish.graph` compiles into a launch plan over one arena
(`tilefish.plan`) that runs from Python and captures in a CUDA graph
(`tilefish.capture`). A lowered kernel also compares, selects, gathers and
scatters rows and reduces to an index, broadcasts along any axis, and may use
IEEE f32 math (`math="ieee"`), `tilefish.tanh`, CUDA's `erff`, `__sinf`,
`__frcp_rn`, `fmaf` and negation, and sums in a fixed order (a sequential
chain, or lanes and a tree as a CUDA block adds); `tilefish.im2col1d` and
`tilefish.col2im1d` are generated ops for 1-D convolutions; an extern may be a
Gluon kernel or have one implementation per architecture, take TMA tensor
descriptors (`TensorDesc`) and be warp-specialised; a pinned GEMM takes bf16,
f16 or f32 operands, an f32 result, the layouts `TN`, `NN`, `TT` and `NT` and an
SM partition, and its algorithm is chosen as torch chooses it or imported; a
pinned cuDNN forward convolution (`cudnn.conv_fwd`) is a library op too; no
build makes an IEEE f32 dot into TF32 tensor-core MMAs; and the plans exported
together share one manifest and can share one arena; the arithmetic written
in a graph body is fused into kernels tilefish generates, byte for byte the
composition of one kernel per op. A Rust host (the
`tilefish` crate, `crates/tilefish`) loads a manifest directory and launches
its cubins, its GEMMs and convolutions and its plans
(`LaunchPlan`, `CapturedPlan`, `PlanSet`, `SharedArena`), with typed launchers generated by
`tilefish.hosts.rust.emit`. A C++ host (`crates/tilefish-capi`: a C ABI over the
crate, `tilefish.h`, and the C++17 wrapper `tilefish.hpp`) runs the same, with
typed launchers and plan runners generated by `tilefish.hosts.cpp`. The
`tilefish build` command is still the plan.

Building for sm_103 needs a newer `ptxas` than the one Triton 3.5.1 bundles
(CUDA 12.8's, which cannot target `sm_103a`): set `TRITON_PTXAS_PATH` to the
`ptxas` of CUDA 12.9 or newer. A build that fails for this reason says so, and
the GPU tests that build for an architecture the `ptxas` cannot target skip,
naming it.

## Why

In inference code the contract of a kernel is usually written three times and
checked by none of them:

- the shape, dtype, alignment and aliasing rules sit in a docstring, a few
  `assert`s and a comment above a C ABI;
- a block-scaled weight format (MXFP8, MXFP4, NVFP4) is described in prose,
  together with the per-architecture byte layout of its scales;
- the same kernel is ported by hand from Triton to CUDA C++ to Rust, and parity
  tests chase the last ULP (FMA contraction, flush-to-zero, reduction order)
  after the fact;
- which implementation runs at which `(M, N, K)` on which GPU is a table
  someone measured once.

tilefish moves all of that into types, so the compiler can check it, generate
it and reason about it.

## What it looks like

```python
import tilefish
from tilefish import Dim, Tensor, InOut, Out, BlockScaled, const
from tilefish import bf16, f32, e4m3, e2m1, ue8m0

M = Dim("M")                          # runtime dimension
D = Dim("D", 2560)                    # static: baked into the binary
H = Dim("H", 1024)
F = Dim("F", 3072)
K = Dim("K", divisible_by=32)         # constraint, checked at build time
N = Dim("N", divisible_by=128)

mxfp8 = BlockScaled(elem=e4m3, scale=ue8m0, block=32, axis=-1)
mxfp4 = BlockScaled(elem=e2m1, scale=ue8m0, block=32, axis=-1)
nvfp4 = BlockScaled(elem=e2m1, scale=e4m3, block=16, global_scale=f32)

# A kernel whose body tilefish understands: it can be fused, and it is
# lowered to Triton.
@tilefish.kernel
def residual_add_rmsnorm(
    x: Tensor[M, D, bf16],
    residual: InOut[Tensor[M, D, f32]],
    w: Tensor[D, bf16],
    *, eps: const[f32] = 1e-6,
) -> Tensor[M, D, bf16]:
    r = residual + x.to(f32)
    residual[...] = r
    rstd = tilefish.rsqrt(tilefish.mean(r * r, axis=-1, keepdims=True) + eps)
    return (r * rstd * w.to(f32)).to(bf16)      # the only rounding point

# An existing hand-written kernel, unchanged, given a type.
n = Dim("n", divisible_by=16)

# (index_bits=32 is the default: a kernel that offsets with i32 gets a max_elements
# limit of 2**31 - 1 on every tensor, which both hosts check; a kernel that
# indexes in i64 says index_bits=64.)
@tilefish.extern(triton=my_kernels.gelu, num_warps=4,
                 grid=lambda n: (tilefish.cdiv(n, 1024),))
def gelu(x: Tensor[n, bf16], y: Out[Tensor[n, bf16]],
         n_elem: n, BLOCK: const = 1024): ...

# A library operator: opaque body, typed signature, pluggable epilogue.
@tilefish.library("gemm", acc=f32)
def gemm(a: Tensor[M, K, bf16], b: Tensor[N, K, mxfp8]) -> Tensor[M, N, bf16]: ...

# A model is ordinary Python over typed values.
@tilefish.graph
def mlp(x: Tensor[M, H, bf16], w_gu: Tensor[2 * F, H, mxfp8], w_d: Tensor[H, F, mxfp8]):
    g, u = gemm(x, w_gu).split(F, axis=-1)
    a = (tilefish.silu(g.to(f32)) * u.to(f32)).to(bf16)
    return gemm(a, w_d)
```

## How a build works

```sh
tilefish build --arch sm_90,sm_100,sm_120 --host python,rust,cpp
```

1. Trace the graph into a typed IR and check it: shapes, dtypes, divisibility,
   aliasing, and which architectures each operator supports.
2. Run the rewrite rules (below) and settle the final list of kernels.
3. Lower each `@kernel` to Triton source, written to disk for review.
4. Derive Triton's compile inputs from the types: pointer dtypes and 16-byte
   alignment, `constexpr` values from static dimensions, divisibility hints
   from `divisible_by`, and one binary per bucket for bucketed dimensions.
   Compile ahead of time to one cubin per architecture.
5. Write a manifest: symbol, parameter ABI in order, grid rule, block size,
   shared memory, launch attributes, toolchain versions, and a digest of the
   machine code.
6. Generate the hosts from the manifest and the types: a `torch.library`
   custom op for Python, a header for C++, a `cudarc` crate for Rust. Every
   precondition that selected a binary (alignment, divisibility, static sizes)
   becomes a check in the generated launcher, so no host can run a binary
   under assumptions it was not compiled for.

Library operators put a different code object behind the same kind of
manifest entry: a CUTLASS instantiation with a C entry point, a CuTe DSL
ahead-of-time export, or a pinned cuBLASLt algorithm recorded with its
workspace size and replayed as is (the last exists: a bf16 GEMM, below).

The Python side has three modes:

| mode | what runs | used for |
|---|---|---|
| `jit` | the current source, built through its compile spec (the path of the build) in memory and launched through the CUDA driver | iterating on a kernel |
| `reference` | the same bodies interpreted with torch | an oracle, compared within a tolerance |
| `replay` | the prebuilt cubins of a manifest directory, checked against its digests, through the CUDA driver; it needs a trust anchor, the manifest's pinned digest or an explicit `trust_directory=True` | the exact machine code the C++ and Rust hosts run |

```python
y = tilefish.run(residual_add_rmsnorm, x, residual, w)                        # jit
m = tilefish.runtime.export(residual_add_rmsnorm, "build/")                    # cubins and manifest.json
y = tilefish.run(residual_add_rmsnorm, x, residual, w, mode="replay", manifest="build/", pin=m.digest)           # a manifest whose digest you hold
y = tilefish.run(residual_add_rmsnorm, x, residual, w, mode="replay", manifest="build/", trust_directory=True)  # whatever the directory holds
```

`replay` refuses to run without one of the two (`pin=` or `trust_directory=True`). This
is a deliberate breaking change in 0.0.x: until 0.0.2 a replay trusted the directory by
default, and the digests in it sit next to the files they describe, so whoever can write
the directory could make it run any binary.

A pin is of one exported artifact, not of a recipe: the manifest digest covers the cubin
files byte for byte. Exports are reproducible. A cubin's debug sections name each source
by its module path (`kernels/rms.py`, `tilefish_generated/softmax.py`,
`triton/language/standard.py`), not by the checkout, the virtual environment or a scratch
directory, and a generated kernel's source is written to a file addressed by its sha256.
So the same graph exported again with the same toolchain (Triton, `ptxas`, cuBLASLt,
cuDNN) on the same kind of device, from another directory, in another process or on another
machine, gives the same files, the same manifest digest and the same plan digest, and a
recorded pin checks a rebuild. A manifest exported by tilefish 0.0.6 or earlier names the
directory it was built in; it loads and replays as before, and only its digest is not what
a new export of the same graph gives. Pin what you exported, and ship that directory.
For a profiler that wants the absolute source paths in the cubins (rather than resolving
`kernels/rms.py` against a source directory), build with `TILEFISH_DEBUG_PATHS=absolute`.
It is off by default and breaks reproducibility: that export's cubins, `sha256`s and digests
name where it was built (the `sha256_code`s are the same), and its binaries are cached apart.

Arguments are torch tensors, matched to the signature the way a call is
matched in a trace: inputs and `InOut` tensors are passed (an `InOut` tensor
is updated in place), `Out` tensors are allocated and returned. Before a
launch every precondition of the binary is checked (dtypes, static sizes,
`divisible_by`, 16-byte aligned pointers, contiguity), and a bucketed
dimension must equal a bucket exactly: there is no padding.

`jit` and `replay` launch the same way, so they run the same machine code: a
cubin that `jit` builds has the `sha256_code` of the one in the manifest.
`replay` refuses a cubin whose digests are not the manifest's, a manifest
entry that is not what the operator's compile spec asks for, and a stale
binary: a kernel redeclared with another body but the same name and signature
does not replay its old binary.

**What a binary is, is the Triton IR its kernel compiles to.** Which kernel
Triton compiles depends on everything the Python process holds when its
frontend runs: the text of the function and of the jit functions it calls, the
module constants it reads (`cfg.SCALE`, `getattr(cfg, "SCALE")`, `getattr(cfg,
"SC" + "ALE")`, a class attribute `cfg.Inner.SCALE`), closure variables, a
`triton.constexpr_function` that reads the environment, a `tl.constexpr` of an
object whose `repr` hides its state, a helper two modules away, a user module
named like a standard library module. Five rounds of review found a route that
each way of *looking for* these (a digest of the files a kernel reaches, the
module attributes, the closures, a watch on the imports) did not follow, and each
was a stale binary served by the build cache or by an export replayed with a
pin. So nothing is looked for. Triton's frontend folds every one of them into
the IR it builds, and that IR is hashed (`tilefish._ir`): the TTIR that
`ASTSource.make_ir` builds, printed with `Module.str_nodebug()` (no locations,
no names of values). Where the kernel is (its path, its line numbers), comments,
blank lines and the names of local variables are not in it, so none of them is an
edit; the operations, the types, the constants and the functions that are called
are. Whatever the process holds is what is hashed, because that is what is
compiled. The digest of every build is in `BuiltKernel.ir_digest`, and in the
manifest entry as `source_digest` with `source_digest_kind` `"tilefish.triton-ir.v1"`
(the fields schema 2 already had, so a reader of the manifest reads it as before;
a lowered kernel has its `source_sha256` as well, which needs no Triton). A Gluon
kernel's IR is the TTGIR that Gluon's frontend (`GluonASTSource`) builds, with its
layouts and `num_warps` in it, and its kind is `"tilefish.gluon-ir.v1"`.
`replay` recomputes the digest from the kernel the process holds, when Triton
can be imported and is the version that built the entry, and refuses a mismatch
as stale, with a pin or not (without Triton, or with another version, whose IR
may print differently, only a pin vouches for a hand-written kernel; the versions
are compared first, so a Triton whose frontend differs is never asked to run it).
The frontend costs 2 to 8 ms per kernel on a B300 (no compile, no GPU), once for
each build, `jit` call and `replay` call. It runs under the same lock as a
compile, so no two frontends, a compile's own included, run at once in any threads.

So an edit that was not reloaded is not a special case. `export` in the process
that imported the module compiles, and stamps, what that process holds; a fresh
process with the edited file computes another digest and refuses the manifest.
Triton's own `cache_key` is not used, and a build never reads Triton's disk
cache. What was removed: the digest of the files a kernel reaches, the import
watch (`SourceFileLoader.exec_module` is not wrapped and `TILEFISH_IMPORT_WATCH`
is gone), the snapshot of module attributes and the refusal of a reassigned one
(a value that a program assigned is in the IR), and the walk over the values
and closures of a kernel with its refusal of a value that has no stable `repr`.
What stays: the check, for a *lowered* kernel, that its module file has the
`source_sha256` of its spec and that the function the process holds was
imported from those lines (the IR digest says what the process holds, not that it
is the source the spec claims); that `build(spec, fn=)` compiles the function
the spec names and no other; and the refusal of whatever makes Triton compile
something other than the IR: its kernel override (`TRITON_KERNEL_OVERRIDE`) and
the compile option `ir_override` replace the IR of a stage with a file (so the
binary would not be of the IR), and an active instrumentation plugin
(`CUDABackend.instrumentation`) patches the passes.

A build compiles from scratch (25 to 120 ms per binary on a B300) unless
tilefish's own cache has it: `~/.cache/tilefish`, or `$TILEFISH_CACHE_DIR` (an
empty value switches it off; `aot.build(..., cache=False)` skips it for one
build). Its key is the cache recipe (a number that is bumped whenever tilefish
changes what goes into a binary) and the tilefish version, the IR digest, the
compile options, the architecture, the Triton and `ptxas` versions, and the
Triton settings that change code generation: every environment variable of the
families `TRITON_`, `MLIR_`, `LLVM_`, `NVPTX_`, `AMDGCN_`, `DISABLE_`, `ENABLE_`,
`ALLOW_` and `USE_IR_LOC` except those known not to (cache and dump directories,
tool paths, debugging switches), which is more than the 30 that Triton lists as
cache-invalidating (it leaves out `TRITON_LIBDEVICE_PATH`,
`TRITON_MOCK_PTX_VERSION` and `TRITON_KERNEL_OVERRIDE`, among others), the
effective value of each codegen knob of `triton.knobs` and the sha256 of the
libdevice file when a path is set. A setting that names a file Triton reads is
keyed by the sha256 of the file, not by its path, so a file rewritten under its name
is another binary: the compile option `extern_libs`, `TRITON_LIBDEVICE_PATH` and
`LLVM_PASS_PLUGIN_PATH` (a file that cannot be read refuses the build); the rest
of what Triton 3.5.1 has that names a path is a tool (`ptxas`, whose version is in
the key), an output, or the launcher's, and `_cache.py` lists it. Every read is verified: the `sha256` and
`sha256_code` of the cubin are recomputed (and the PTX, the entry point and its
ABI, the options, the IR digest and the versions are checked), and an entry that
is not as it was written is a warning and a rebuild, never used, and a cache
that cannot be read or written never fails a build, also under `python -W error`
(the warning is then logged on `tilefish.cache` instead of raised). Entries are
written through a temporary file and renamed, so builds that race do not tear
one. A lookup is a run of the frontend and a read: 3 to 6 ms. Nothing evicts the
cache, it is no defence against someone who can write the directory (a manifest
is what to pin), and it tells a patched Triton that keeps its version string from
the original no better than the version does. The same directory holds, under
`generated/<sha256>/tilefish_generated/`, the Triton source of each lowered kernel
and generated op (Triton reads a kernel's source from a file): written atomically,
used only when it holds exactly that source, and, when the directory cannot be
written, kept in a private scratch directory of the process instead (with one
warning). Where it is does not reach a binary.

`replay` also refuses `shared` memory the cubin and the device cannot have (the
driver's static shared memory of the function plus the manifest's dynamic size
must fit the device's opt-in maximum), an argument list that does not fit the
ABI, and a grid beyond the device's limits. The manifest is read as strict JSON
(no duplicate keys, no `NaN`, no number that does not fit a float), files are
written through a temporary file and renamed, and a symbolic link where a file
is to go is refused.

**An IEEE f32 dot is not built into TF32 MMAs.** A tensor core has no f32 multiply: an f32 MMA rounds its inputs to TF32, 10 of the 23 bits of
the mantissa. Triton 3.5.1 nevertheless compiles some `tl.dot(a, b, input_precision="ieee")` of f32 operands to `tcgen05.mma ... kind::tf32` on
sm_100 and sm_103: its MMAv5 path skips the precision check when an operand derives from a load narrower than 32 bits (an f16 or bf16 tile
converted to f32) or from `tl.join`, and the tile has `M % 64 == 0`, `N % 16 == 0` and 4 or 8 warps. Measured on a B300 with `a = 1` (f16),
`b = 1 + 2**-12`, 16 terms: every output is 16 instead of `16 + 2**-8`; the same kernel at `M = 32`, or on sm_90 and sm_120, is exact. So every
build (`jit`, `export`, a plan, a cache hit) refuses a kernel whose IR asks for an IEEE f32 dot when its binary has TF32 tensor-core MMAs made of
such a dot (`tilefish._tf32guard`). The check reads what the compiler made, not a copy of Triton's rule: the dots and their precision in the TTIR
the frontend builds, and the TF32 MMA instructions of the PTX (`tcgen05.mma` of `kind::tf32`, `wgmma` and `mma.sync` of `.tf32` operands). A kernel
whose f32 dots all ask for IEEE is refused when its binary has any TF32 MMA; one that also has dots that allow TF32 is judged dot by dot, each `ttng.tc_gen5_mma` of
its TTGIR traced to the TTIR dot it was made of by source location, and an MMA it cannot trace is refused too. A dot that says
`input_precision="tf32"` or `"tf32x3"` asks for TF32 and is never refused. The error names the dot and the fixes: a tile of fewer than 64 rows
for that dot, the product written as a loop of `tl.fma` (no `tl.dot`), or `input_precision="tf32"` where TF32 is what the kernel may compute.
Gluon kernels are checked the same way (in Triton 3.5.1 Gluon has no IEEE f32 dot that compiles: `warpgroup_mma` refuses one, and `tcgen05_mma`
of f32 operands is TF32 by the kernel's own choice); a lowered `@kernel` has no dot. A prebuilt PTX or cubin has no IR to say what it asked for and
is not checked, and neither is a manifest exported before this check (re-export it).

**Trust.** A replay needs a trust anchor, `pin=` or `trust_directory=True`, and
raises without one. The digests in a manifest directory sit next to the files
they describe, so whoever can write the directory can rewrite both.
`export` returns the manifest with its `digest`, a sha256 over every entry, and
checks that the directory it wrote has that digest; keep it somewhere you trust
and pass it as `pin=` to refuse a directory that changed.
`trust_directory=True` is the explicit statement that whatever the directory
holds is fine (a directory you wrote a moment ago); it does not combine with
`pin=`. A pin vouches for the manifest, not for an IR digest that is known to
differ, and not for a `shared` that is nonzero but too small for the kernel
(nothing but the manifest says how much it needs: the cubin of a Triton kernel
does not record its dynamic shared memory, measured in
`python/tests/test_gpu_shared_size.py`; the export writes Triton's value, which
the pin covers, and `trust_directory=True` trusts it with the cubins). Triton's own JIT launcher,
which specializes on argument values, is not a mode. Neither `jit` nor `replay`
needs a C compiler, and a `replay` of a generated kernel needs neither Triton nor
`ptxas`.

CI asserts, on a GPU (the tests marked `gpu`), that a `jit`-built cubin has the
digest of the manifest's, that `jit` and `replay` agree byte for byte, and that
`replay` stays within tolerance of `reference`. The tolerances are measured per
input distribution and dtype (f32, bf16 and f16 in and out; normal, uniform,
heavy-tailed, sparse outliers, values of every magnitude) and tabulated in
`python/tests/test_gpu_reference.py`: a ULP
count only means something where the result is far from zero (a layernorm of
data with a large mean has tiny outputs), so a bf16 output is bounded by half a
bf16 step of the largest reference value and a fraction of elements that may
differ, the f32 softmax by an absolute error of 5e-7, the gelu by 3e-5. An
experiment that passes in `replay` is, kernel for kernel, what production runs.

## Views, device scalars, prebuilt binaries and a pinned GEMM

A real model needs four things that a dense, compiled-in, Triton-only operator cannot say. Each is part of the manifest, which is schema 3
(`docs/manifest-schema-3.md` specifies every field; the Python package reads and writes only schema 3, and says "re-export" for schema 2).

**Strided views.** A tensor type has element strides and an element offset, in the dimension algebra (`TensorType.strides`, `.offset`); dense
and 16-byte aligned (`contiguous`) is the default. `x.reshape(M, 3, H, D)` (a dense input), `x.permute(1, 0, 2)`, `x[:, 1]` / `x.select(axis, i)` and
`x.split(...)` copy nothing: they are views with the strides and the offset of the operation. A split whose number of chunks depends on a
dimension (`x.split(16, axis=1)` of `x: [M, C]` with `C = Dim("C", divisible_by=16)`) returns `Chunks`, a sequence of symbolic length:
`chunks[0]` and `chunks[-1]` always exist, any other chunk where the dimension's smallest size proves it, and `len()` and unpacking
raise. A stride or an offset may be a product of
symbolic sizes: an `[H, L, L]` tensor has the stride `L*L` along its first axis, and `x[h]` the offset `h*L*L` (`tilefish.dims.mul`; a shape stays
affine, `L * L` is still refused there, and only a launch grid may multiply dimensions), which a `Strided[...]` argument binds and a plan evaluates at every bucket, so attention
scores `[H, L, L]` are a buffer of a plan and their transposes and heads are views of it. A view is a `View[...]` and can go into traced
elementwise and reduction ops; a declared operator takes one only where its parameter says so. Every other tensor parameter (and result) of a kernel,
extern, library op or graph is contiguous: an annotation that is a `TensorType` with other strides, an offset or no alignment is refused at the
declaration, and a launch refuses a tensor that is not contiguous for such a parameter. An `extern` parameter `x: Strided[Tensor[S, H, D, bf16]]`
takes a view, and the kernel's strides are scalar parameters the stub declares in the kernel's argument order:

```python
@tilefish.extern(triton=head_copy, grid=lambda S: (S, 8))
def head_copy(x: Strided[Tensor[S, 8, 64, bf16]], y: Out[Tensor[S, 8, 64, bf16]],
              x_s0: StrideOf("x", 0), x_s1: StrideOf("x", 1), D: const = 64): ...      # the last axis has stride 1

y = tilefish.run(head_copy, qkv[:, 1])        # a view of a fused qkv tensor: its pointer and its two strides go to the kernel
```

A kernel that reads several views of one buffer with **one** stride pair (the q, k and v column blocks of a fused `[B, 3 * D]` tensor) declares the stride
once for all of them, `s_row: StrideOf(("q", "k", "v"), 0)`: the views share the stride dimension, so a call binds it from `q` and refuses a `k` or a `v` that
does not have it (a trace call, a launch in Python and in Rust, and every step of a plan), and the kernel is given the stride once and a pointer per view.

An axis without a `StrideOf` must be the last one (its stride is then 1, and a view that does not have it is refused); the strides are bound at a
call like shapes are, range-checked as `i32` (`i64` for `index_bits=64`), and a strided pointer is bounded by its extent (`max_extent`), not its element
count. The type of a stride scalar is the width of the offsets unless the `StrideOf` says otherwise: a kernel that takes `i32` strides and computes
64-bit offsets with them (`row.to(tl.int64) * s_row`) declares `index_bits=64` and `s_row: StrideOf("x", 0, dtype=tilefish.i32)`, and a launch then holds
the stride to an `i32` and the extent of the view to nothing. The pointer passed is `base + offset * itemsize`. `Strided[Tensor[...], 16]` compiles the kernel for a 16-byte aligned pointer
(`tt.divisibility=16`), which the offset must then provably allow (a trace call refuses an offset that is not a multiple of 16 bytes, a launch
checks the address); without the `16` Triton gets no hint and any element-aligned view runs. Lowered `@kernel`s still take contiguous tensors only: a
view in a kernel body is refused with the rule that says so.

**Views that do not start on 16 bytes, given to a lowered kernel.** Every pointer of a lowered kernel is compiled as 16-byte aligned, so a dense view that
does not provably start on 16 bytes, such as a row `plane[k]` of a `[K, R]` int32 plane with an odd `R`, is not a contiguous tensor. Such a view given to a
read-only parameter runs the kernel's **specialisation** for it: `kernel.unaligned("a")`, the same kernel with `a` compiled aligned to its element only (no
`tt.divisibility` for it, a `pointer_alignment` of its element size that every launch checks). It is an operator of its own, keyed apart from the kernel
everywhere a binary is (its name `add_rows__ua0`, after the indices of those parameters, its stems, its declaration digest, its Triton IR and so its build cache
key, its manifest entries), and its generated source is the kernel's:

```python
@tilefish.graph
def plane_sum(plane: Tensor[3, R, i32]):
    s = add_rows(plane[1], plane[0])        # plane[1] starts 4 * R bytes in: the step launches add_rows__ua0
    return add_rows(s, plane[2])            # plane[2] starts 8 * R bytes in: add_rows__ua1

y = tilefish.run(add_rows, plane[1], plane[0])   # an address that is not 16-byte aligned runs add_rows__ua0 too
```

A graph's export has the specialisations its plan's steps launch; `tilefish.runtime.export(add_rows.unaligned("a"), directory)` writes one for the kernel
alone, and a replay of a manifest that lacks it says so (`docs/manifest-schema-3.md`, section 6).

**Device scalars.** `n_tok: DevScalar[i32]` is one element in device memory: in the ABI a pointer with the shape `[]`, at the API a tensor of one
element. A binary reads it with `tl.load`, so one binary serves every value and a value changes by writing memory, never by building; a lowered kernel
reads it with `tilefish.load(s)` (one `tl.load(ptr)`, broadcast).

**A dimension only an `Out` tensor has.** An extern may write a tensor whose size no input has: `key_mask(mask: Out[Tensor[B, bf16]], n_valid: DevScalar[i32],
b: B)` makes a `[B]` mask from a device scalar alone. A launch binds `B` from the `Out` tensor it is given (`tilefish.run(key_mask, n, outputs=mask)`; a Rust
launch and every plan step have their `Out` tensors) and checks it like any dimension, buckets included. In a graph the call binds `B` to the graph's own `B`
(the same `Dim`), so the plan, which is per bucket, sizes the mask and the step binds it from that buffer.

**Prebuilt binaries.** `@tilefish.extern(ptx="k.ptx", symbol="k", block=(256,), grid=...)` or `cubin={"sm_103": "k.cubin"}` declares a kernel that
Triton does not compile, by its C ABI: pointers, `Dim` scalars and typed `const[i32|i64|f32]` fixed arguments, in order, and **no Triton scratch slots**.
Its identity is the sha256 of the bytes of the file (`source_digest` of kind `tilefish.binary.v1`); PTX is assembled by `ptxas` with fixed, recorded flags
(the ones Triton passes, so the PTX of a Triton build declared this way gives the machine code, and the output bytes, of the Triton path); a cubin is used
as it is for its own architecture and refused for another. `replay` refuses a file that is not the one the manifest was built from.

A `const[i32]` or `const[i64]` of a prebuilt binary **without a default** is a fixed argument *given per call*: the geometry of a call (an output
size, an offset) that no tensor determines. One declaration and one binary serve every value: `k(x, h_out=5)`, `tilefish.run(k, x, h_out=5)`,
Rust `Kernel::launch_with(stream, tensors, &[("h_out", 5)])`; in a graph the value may be an expression of the graph's dimensions (`h_out=H // 2`),
and each step of the plan records the values of its call at its bucket (`"given": {"h_out": 5}`), so they are in the plan's digest and both hosts
check them against the entry (`docs/manifest-schema-3.md`, section 5.3).

**Null pointers and 64-bit dimension scalars.** A pointer an extern's kernel does not use in the declared use (a bias it reads only when it is not
null, or only under a constexpr flag the declaration turns off) is declared `Null[dtype]`: a call does not pass it, and both hosts pass the null pointer
at its slot (manifest kind `null`, section 5.6). A dimension scalar is an `i32` unless it is declared `i64[n]`: the same scalar passed as an `i64`, its value
still derived from the shapes and checked against them, for a kernel whose count is 64 bits wide (section 5.7). Both together:

```python
@tilefish.extern(ptx="scale_bias.ptx", symbol="scale_bias_f32", block=(256,), grid=lambda n: (tilefish.cdiv(n, 256),), index_bits=64)
def scale(x: Tensor[n, f32], bias: Null[f32], out: Out[Tensor[n, f32]], n_elem: i64[n]): ...    # (const float*, const float*, float*, long long)
```

**Gluon kernels.** A kernel written in Triton's Gluon dialect (`triton.experimental.gluon`: `@gluon.jit`, layouts written out, so the kernel pins
which thread holds which element and so the order of its reductions) is declared with `gluon=` in place of `triton=`, and everything else is the same:
strided views and shared strides, `const` arguments, buckets, `index_bits`, `enable_fp_fusion`, plans, `jit`, `replay` and the Rust host.

```python
@tilefish.extern(gluon=my_gluon_kernels.row_sum, num_warps=4, grid=lambda R: (tilefish.cdiv(R, 4),), index_bits=64)
def row_sum(x: Strided[Tensor[R, 256, f32]], y: Out[Tensor[R, f32]], s_row: StrideOf("x", 0, dtype=tilefish.i32), n_rows: R, C: const = 256): ...
```

The declaration says which frontend compiles the kernel because a compile spec is the whole recipe of a binary, made from the declaration without
importing the kernel: `"language": "gluon"` is in the spec and in the declaration digest, and the build hands Gluon's `GluonASTSource` to
`triton.compile`. Its identity is the TTGIR that frontend builds (`source_digest_kind` `"tilefish.gluon-ir.v1"`, under its own tag), so a changed
layout, `num_warps`, body or constant is another binary, and `replay` refuses a stale one, pinned or not, as for a Triton kernel. A Gluon kernel given as
`triton=` (or a `triton.jit` one as `gluon=`) is refused with the argument to use: at the declaration for a kernel object, at the build for a
`"module:function"` string. The manifest entry is a `triton` entry (Triton compiled it; it has the two scratch slots), so a host launches it like any other.

**An implementation per architecture.** The fastest kernel that gives the bits a model needs can differ by GPU: Triton lowers the same `tl.dot` to other
instructions on other architectures, and those may add the products of a wide dot in another order. One declaration can say so:

```python
@tilefish.extern(
    by_arch={
        "sm_103": tilefish.impl(triton=my_kernels.row_sum_tiled, num_warps=8, consts={"ROWS": 4}),
        "sm_120": tilefish.impl(triton=my_kernels.row_sum, num_warps=4),
    },
    fallback=None,                                       # or a tilefish.impl(...) for every other architecture
    grid=lambda R, ROWS: (tilefish.cdiv(R, ROWS),),      # an impl may have its own grid=
)
def row_sum(x: Tensor[R, 1024, f32], y: Out[Tensor[R, f32]], n_rows: R, ROWS: const = 1): ...
```

The op is one typed signature for a graph, a plan, a caller and `reference=` mode. `export` builds the implementation of the target architecture (`arch=`,
or the device's), `jit` the one of the device's, and both refuse an architecture that has neither its own nor a `fallback`. Each implementation is a Triton or
Gluon kernel with its own compile options (`num_warps`, `num_stages`, `enable_fp_fusion`), constexpr values (`consts=`) and `grid=`; every one takes the stub's
parameters and has the same launch ABI, buckets, dimensions and preconditions, which the declaration checks, so a plan is the same document whichever runs
and a host launches each the same way. Each is an op of its own (`row_sum.for_arch("sm_103")`, `tilefish.aot.compile_specs(row_sum, arch=103)`): its key is in
its declaration digest and its compile specs, and its manifest entries record it (`"implementation": "sm_103"`, or `"fallback"`;
`docs/manifest-schema-3.md`, section 4.1). `replay` selects the implementation of the device's architecture as the export did, so an entry of another
implementation, or of one that changed (its kernel, options, constants or grid), is refused as stale; another architecture's implementation changing
leaves this architecture's manifest valid. The Rust crate reads the field (`Entry::implementation`) and launches the entry of its device's architecture.

An implementation can be shared, be a prebuilt binary, and have an ABI of its own:

```python
def row_sum_tma(x: TensorDesc(Tensor[R, 1024, f32], block=(64, 1024)), y: Out[Tensor[R, f32]], BLOCK_R: const = 64): ...

@tilefish.extern(
    by_arch={
        "sm_100": tilefish.impl(triton=my_kernels.row_sum_tma, stub=row_sum_tma, grid=lambda R: (tilefish.cdiv(R, 64),), name="tma"),
        "sm_103": tilefish.impl(triton=my_kernels.row_sum_tma, stub=row_sum_tma, grid=lambda R: (tilefish.cdiv(R, 64),), name="tma"),
        "sm_120": tilefish.impl(ptx="row_sum_sm120.ptx", symbol="row_sum", block=(256,)),   # the op's stub is its C ABI
    },
    grid=lambda R: (R,),
)
def row_sum(x: Tensor[R, 1024, f32], y: Out[Tensor[R, f32]], n_rows: R): ...
```

`name="tma"` makes one implementation of every architecture mapped to it: one key (`"implementation": "tma"`), one declaration digest, one set of compile
specs (without a name each architecture has its own, as before). `ptx=` / `cubin=` with `symbol=` and `block=` is a prebuilt binary; a cubin implementation
needs a cubin for every architecture that runs it. `stub=` lists the kernel's own parameters, so one implementation takes a tensor as a TMA descriptor
where another takes a pointer, with other scalars, constexprs or fixed arguments. What every implementation must share is the op's public signature: its
tensors (names, order, access, dtype, shape, `Strided` or not), its fixed arguments per call and its buckets, which is what a caller, a plan step and a typed
Rust launcher bind. Each manifest entry carries its implementation's ABI, and a plan is checked against every implementation, so it never relies on an
architecture.

**TMA descriptors.** A Hopper or Blackwell kernel in Triton or Gluon gets its best speed from the Tensor Memory Accelerator, which takes a *tensor
descriptor*: a 128-byte `CUtensorMap` that the host encodes (`cuTensorMapEncodeTiled`) and passes by value. A parameter declared `TensorDesc(...)` is one:

```python
@tilefish.extern(gluon=my_gluon_kernels.tma_copy, num_warps=4, grid=lambda R, C: (tilefish.cdiv(R, 64), tilefish.cdiv(C, 64)))
def tma_copy(x: TensorDesc(Tensor[R, C, f16], block=(64, 64)), y: Out[TensorDesc(Tensor[R, C, f16], block=(64, 64))]): ...

y = tilefish.run(tma_copy, x)    # a call passes the tensor: the host encodes its descriptor (address, shape, strides) for this launch
```

The declaration says the block (the tile one `load` or `store` moves), the swizzle (by default the largest the block's rows allow; a Gluon kernel's type has it,
a Triton kernel's compiler picks one and the build refuses a declaration that is not its choice), the L2 promotion and the out-of-bounds fill (`"zero"`: a
coordinate outside the tensor, a negative row included, reads zeros); the box of the map is the block with its rows cut to the swizzle span. The kernel is
launched with the map, then the tensor's shape (`i32` each) and strides (`i64` each), exactly as Triton 3.5.1 launches a host `TensorDescriptor`, so the
bytes are those of Triton's own launch (`test_gpu_tma.py` compares them). The manifest records each descriptor (kind `tensordesc`, its `tensor_map`: every
argument of the encode but the tensor's; manifest schema 3, section 5.5), and both hosts check what the driver would refuse before they encode (a 16-byte
address: `pointer_alignment`; strides that are multiples of 16 bytes and dimensions within `i32`: `tensor_map`). A map is encoded at every launch from the
tensor of that launch, and for a plan at every execution from the buffers each step binds; a CUDA graph holds the maps of the addresses it was captured
with, as it holds the addresses. `TensorDesc(Strided[Tensor[...]], ...)` describes a view the kernel reads (its row stride is the view's). Triton's
*device-side* descriptors (`tl.make_tensor_descriptor`) write their maps into a global scratch, which an extern declares (`global_scratch=`, below).

**Warp-specialised kernels.** A Blackwell kernel is often fastest when its partitions run on warps of their own: Gluon's `gl.warp_specialize` (a
1-warp TMA producer and a 1-warp MMA issuer feeding 4 compute warps, say), or Triton's own warp specialisation of a `tl.range(..., warp_specialize=True)`
loop. Such a kernel is declared like any other:

```python
@tilefish.extern(gluon=my_gluon_kernels.ws_matmul, num_warps=4, grid=lambda M, N: (tilefish.cdiv(M, 128), tilefish.cdiv(N, 128)))
def ws_matmul(a: TensorDesc(Tensor[M, K, f16], block=(128, 64)), b: TensorDesc(Tensor[N, K, f16], block=(128, 64)),
              c: Out[TensorDesc(Tensor[M, N, f16], block=(128, 128))], k_len: K): ...
```

`num_warps` is the warps of the kernel's **default partition** (those its layouts outside the worker partitions are written for; all its warps when it is
not warp-specialised). The workers add warps of their own, and the compiled kernel has the total: Triton 3.5.1 reports 8 for 4 + 1 + 1 (and 12 for
8 + 1 + 1, so declaring 8 would not give 8). The build takes that total from the compiled kernel when its TTGIR has warp-specialised regions, and refuses
any other kernel whose warps Triton changed, as before; either way the PTX's `.reqntid` must be the block. The manifest entry keeps `num_warps` (the compile
option) and records `total_num_warps` with the block it makes (`32 * total_num_warps`; manifest schema 3, section 4.2), which is in the manifest digest, and
every launch takes that block: `jit`, `replay`, a step of a plan, a CUDA graph, and the Rust crate (`Entry::total_num_warps`, `Plan::block()`).

**Launch shapes.** How an extern is launched can say more than an affine grid (manifest schema 3, sections 4.3 to 4.6):

```python
@tilefish.extern(triton=k.scale, grid=lambda T, C, BLOCK: (tilefish.cdiv(T * C, BLOCK),))       # a grid may multiply dimensions
def scale(x: Tensor[T, C, f32], y: Out[Tensor[T, C, f32]], n_t: T, n_c: C, BLOCK: const = 1024): ...

@tilefish.extern(triton=k.tiles, grid=lambda M, N: (tilefish.cdiv(M, 128) * tilefish.cdiv(N, 128),),
                 persistent=tilefish.persistent(programs_per_sm=1))                              # min(tiles, 1 * SMs) programs
def tiles(a: Tensor[M, K, f16], b: Tensor[N, K, f16], c: Out[Tensor[M, N, f16]], k_len: K): ...

@tilefish.extern(triton=k.rows, grid=lambda TB, BLOCK_T: (tilefish.cdiv(TB, BLOCK_T),),
                 by_bucket=lambda TB: tilefish.config(num_warps=2, BLOCK_T=16) if TB <= 256 else tilefish.config(num_warps=8, BLOCK_T=64))
def rows(x: Tensor[TB, 128, f32], y: Out[Tensor[TB, 128, f32]], n_rows: TB, BLOCK_T: const = 32): ...
```

A grid is computed at each launch and never solved, so it may multiply dimensions (one binary for every `T` and `C`). A **persistent** grid is the
number of tiles, and the host launches at most `programs_per_sm` programs per SM of the device it loads the binary on (or of the partition it says it runs
on: `Manifest::with_sm_partition` in Rust, `tilefish.runtime.sm_partition(n)` in Python), so a manifest exported on a MIG slice runs on the whole GPU;
the kernel walks the tiles with a stride of `tl.num_programs(0)`, and promises that its bytes do not depend on how many programs run, unless it states the
SM count it is for (`sm_count=30`: a persistent reduction), which a host on another count refuses. `by_bucket=` gives each bucket of a bucketed
dimension its own compile-time configuration (warps, stages, CTAs, the values of consts), each binary built, keyed and digested with its own.
`num_ctas=2` (Triton's compile option) runs a program on a thread-block cluster of 2 CTAs, and a prebuilt binary declares `cluster=(2, 1, 1)`: both hosts
launch it with `cuLaunchKernelEx` and the cluster, the grid counting clusters. `global_scratch=256` is the global scratch each CTA of the compiled kernel
addresses (device-side TMA descriptors write theirs there), which the build checks against Triton's metadata: Python allocates it per launch, the Rust
crate takes it as the last tensor of a launch (`Plan::tensor_names()` ends with `global_scratch`), and a plan gives its workspace. Profile scratch, PDL
and cooperative launches stay refused.

**A pinned cuBLASLt GEMM.** `@tilefish.library("gemm", acc=f32, impl="cublaslt.gemm")` over `(a: Tensor[M, K, bf16], b: Tensor[N, K, bf16]) ->
Tensor[M, N, bf16]` computes `a @ b.T` with an f32 accumulator and one rounding (`impl="cublaslt.gemm_bias"` adds `bias: Tensor[N, bf16]`, added in f32 before it).
For each `(M, N, K, bias)` (`M` from its buckets) the algorithm that cuBLASLt's heuristic ranks first under a fixed workspace limit (8 519 680 bytes,
torch's default; `workspace_bytes=` changes it) is pinned: its 64 bytes go to the manifest's `library` section with the cuBLASLt version that chose
it and the SM count of the device it chose it on (`sm_count`: a MIG slice has fewer SMs than the whole GPU), and `replay` runs that algorithm and refuses
another cuBLASLt version and a device of another SM count ("re-export the manifest on this device"). `jit` pins in memory the same way, per device, so
`jit` and `replay` run the same algorithm. The binding is ctypes on the `libcublasLt` the process already has loaded (torch's); operands are contiguous and 16-byte aligned (strided
operands are not supported yet).

How the algorithm is chosen is part of the declaration (and of its digest):

```python
# torch's choice: the result is torch.addmm(bias, a, b.t()) byte for byte (torch.mm(a, b.t()) without a bias)
@tilefish.library("proj", acc=f32, impl="cublaslt.gemm_bias", heuristic="torch", allow_bf16_reduction=True)
def proj(a: Tensor[M, 512, bf16], b: Tensor[1536, 512, bf16], bias: Tensor[1536, bf16]) -> Tensor[M, 1536, bf16]: ...

# algorithms chosen elsewhere (a tuner, another engine's pin file), one table per device: the heuristic is not asked there
config = {"id": 21, "tile_id": 11, "splitk_num": 1, "reduction_scheme": 0, "cta_swizzling": 0, "custom_option": 0,
          "stages_id": 20, "inner_shape_id": 0, "cluster_shape_id": 0}
tuned = tilefish.AlgoTable("sm_120", 84, 120804, {(32, 1536, 512, True): config})  # arch, SM count, cuBLASLt version

@tilefish.library("proj32", acc=f32, impl="cublaslt.gemm_bias", algos=[tuned])
def proj32(a: Tensor[32, 512, bf16], b: Tensor[1536, 512, bf16], bias: Tensor[1536, bf16]) -> Tensor[32, 1536, bf16]: ...
```

* `heuristic="torch"` asks the heuristic as torch 2.9's `addmm` does (`at::cuda::blas::gemm_and_bias`): one result, under the workspace limit alone (no
  alignment minimums: torch's pointers are 256-byte aligned, the library's default), with torch's limits by default, 1 048 576 bytes for `gemm_bias`
  (`CUBLASLT_WORKSPACE_SIZE`) and 8 519 680 for `gemm` (`torch.mm` runs `cublasGemmEx` with `CUBLAS_WORKSPACE_CONFIG`'s workspace, and the heuristic under that
  limit answers what it runs; on an sm_90 exactly torch's default is 32 MiB, `workspace_bytes=33_554_432`). With torch's default reduction
  (`allow_bf16_reduction=True`) the result is torch's byte for byte: `test_gpu_cublaslt.py` asserts it over 48 shapes, with and without a bias, on three
  operand sets each, and it was measured on a B300 MIG slice (sm_103) and an RTX 5090 (sm_120) with cuBLASLt 12.8.4, and on the B300 slice with 13.1.0
  (`test_gpu_gemm.py`, 30 shapes). The default posture, `"tilefish"`, adds 16-byte alignment minimums, asks for 8 results and, without the opt-in, gives a
  GEMM with a bias no split-K (below), which torch does not do. It is not torch's, and how often its result is torch's depends on the cuBLASLt version: on
  the 15 biased shapes of `test_gpu_gemm.py`, all of them with 12.8.4, 13 with 13.1.0, whose heuristic ranks a split-K of 3 with f32 partial sums first
  for 32 and 64 x 1024 x 3072 (neither the workspace limit, nor the alignment minimums, nor the number of results asked changes its first answer there;
  the reduction-scheme mask does).
* `allow_bf16_reduction=True` lets split-K add its partial sums in bf16 (`INPLACE`, `OUTPUT_TYPE`: torch's default,
  `allow_bf16_reduced_precision_reduction`), which rounds more than once. Without it the heuristic is asked for f32 partial sums only, and a GEMM with a
  bias for no split-K at all (with the bias epilogue, a split-K with f32 partial sums was measured to round twice: cuBLASLt 12.8.4 on an RTX 5090); an
  algorithm that breaks either is refused by both hosts. The rule stays in the default posture although some split-K algorithms keep the one
  rounding: nothing in the heuristic's answer tells them apart (`docs/numerics.md`, section 4); `heuristic="torch"` gives `addmm`'s bytes.
* `algos=` imports the algorithms (`tilefish.AlgoTable(arch, sm_count, cublaslt_version, {(m, n, k, bias): config})`, a config being the nine
  `cublasLtMatmulAlgoConfig` attributes or the 128 hex digits of a pin): on the device a table is for, each entry pins the table's algorithm, encoded as
  cuBLASLt encodes it and held to the same checks (`cublasLtMatmulAlgoCheck` for the problem, the workspace limit, bf16 partial sums only with the
  opt-in); a device no table is for is refused, never handed to the heuristic.

A manifest entry records them as `heuristic`, `algo_source` and `allow_bf16_reduction`, which are there only when they are not the default
(`docs/manifest-schema-3.md`, section 9). A pin is the configuration the heuristic chose, encoded by the library: the 64 bytes the heuristic returns can carry
bytes that are no part of it, which change from process to process.

**f16, an f32 result, `b` as `[K, N]`.** The operands may be f16 (both of one type), the result f32 (and a bias has the result's type: cuBLASLt takes no
other, measured), and `layout="NN"` takes `b: Tensor[K, N, T]` and computes `a @ b` (the default, `"TN"`, is `a @ b.T` with `b: Tensor[N, K, T]`):

```python
@tilefish.library("up", acc=f32, impl="cublaslt.gemm_bias", layout="NN", heuristic="torch", allow_f16_reduction=True, workspace_bytes=64 << 20)
def up(a: Tensor[M, 7168, f16], b: Tensor[7168, 1536, f16], bias: Tensor[1536, f16]) -> Tensor[M, 1536, f16]: ...   # torch.addmm(bias, a, b), byte for byte

@tilefish.library("down", acc=f32, impl="cublaslt.gemm")
def down(a: Tensor[M, 3072, f16], b: Tensor[1024, 3072, f16]) -> Tensor[M, 1024, f32]: ...   # a @ b.T, rounded once to f32
```

The opt-in to split-K partial sums in the output type is named by the operands' type, as torch's flags are (`allow_f16_reduction` for f16 operands). Under
`heuristic="torch"` with it, the result is `torch.mm` / `torch.addmm` in f16 byte for byte in both layouts (`test_gpu_gemm_f16.py`: 63 shapes, three
operand sets each, measured on a B300 MIG slice with cuBLASLt 12.8.4). An `AlgoTable` row of the layout `NN` is keyed `(m, n, k, bias, "NN")`; a
configuration is encoded with the declaration's types. The entry says the form in `dtypes`, `transa` and `lda` (`docs/manifest-schema-3.md`, section 9.2).

**`a` stored `[K, M]`.** `layout="TT"` takes `a: Tensor[K, M, T]` with `b: Tensor[N, K, T]` and computes `a.T @ b.T`; `layout="NT"` takes it with
`b: Tensor[K, N, T]` and computes `a.T @ b`, for every operand type above:

```python
@tilefish.library("scores", acc=f32, impl="cublaslt.gemm", layout="TT", heuristic="torch", allow_f32_reduction=True)
def scores(a: Tensor[8, M, f32], b: Tensor[1024, 8, f32]) -> Tensor[M, 1024, f32]: ...   # torch.mm(a.t(), b.t()), TF32 off, byte for byte
```

Under `heuristic="torch"` the pin is what torch runs for `torch.mm(a.t(), b.t())` / `torch.mm(a.t(), b)` and `torch.addmm` of a contiguous `a [K, M]`, byte
for byte, for bf16, f16 and f32 (`test_gpu_gemm_layouts.py`, `M` from 2 to 2048; at `M = 1` torch multiplies `a [K, 1]` as the contiguous `[1, K]` it also
is, so a one-row GEMM is declared `TN` or `NN`). The entry says it in `transb` and `ldb` (`docs/manifest-schema-3.md`, section 9.2).

**f32, TF32 off.** f32 operands have an f32 result (and an f32 bias), and are multiplied as f32:

```python
@tilefish.library("proj32", acc=f32, impl="cublaslt.gemm_bias", heuristic="torch", allow_f32_reduction=True)
def proj32(a: Tensor[M, 1024, f32], b: Tensor[3072, 1024, f32], bias: Tensor[3072, f32]) -> Tensor[M, 3072, f32]: ...   # torch.addmm(bias, a, b.t()), TF32 off
```

The compute type is `CUBLAS_COMPUTE_32F`, never `CUBLAS_COMPUTE_32F_FAST_TF32` (what torch's `allow_tf32` selects) nor the bf16x9 emulation of cuBLAS 13
(`CUBLAS_COMPUTE_32F_EMULATED_16BFX9`). Both hosts refuse an f32 algorithm that would not multiply f32 as f32: one encoded for another compute type
(cuBLASLt writes it into the 64 bytes, and the TF32 and emulated algorithm ids cannot be encoded under `CUBLAS_COMPUTE_32F` at all), one whose
numerical-implementation flags say TF32 or 16-bit inputs, and every f32 pin in a process where cuBLASLt runs `CUBLAS_COMPUTE_32F` as TF32
(`NVIDIA_TF32_OVERRIDE=1`) or as the emulation (`CUBLAS_EMULATE_SINGLE_PRECISION=1`): measured, the encoding shows both. The opt-in to split-K partial sums
in the output is `allow_f32_reduction`; torch has no such flag and never restricts the reduction of an f32 GEMM, so its choice needs it. Under
`heuristic="torch"` with it and torch's workspaces (8 519 680 bytes for `mm`, `CUBLAS_WORKSPACE_CONFIG`'s; 1 MiB for `addmm`), the result is `torch.mm` /
`torch.addmm` in f32 with TF32 off, byte for byte, in both layouts (`test_gpu_gemm_f32.py`: 756 of 756 runs, 63 shapes with `M` from 1 to 2048, three
operand sets, `mm` and `addmm`, `TN` and `NN`, with the default workspace and with `CUBLAS_WORKSPACE_CONFIG=:4096:8` and a 32 MiB limit; measured on a B300
MIG slice with cuBLASLt 12.8.4 and 13.1.0 and on an RTX 5090 with 13.1.0). torch's `mm` runs `cublasSgemm`, and cuBLAS chooses for it the algorithm the
cuBLASLt heuristic answers under that posture. See `docs/manifest-schema-3.md`, section 9.2.

**SM partitions.** On a green context (a partition of the device's SMs) every SM-count query still reports the device's count, and a pinned
algorithm computes the same bytes with or without a partition (measured, cuBLASLt 12.8.4); what changes is the heuristic's choice, through the
context of the process's first cuBLASLt handle. `sm_count_target=P` pins the algorithm the heuristic chooses for `P` SMs
(`CUBLASLT_MATMUL_DESC_SM_COUNT_TARGET`, which every check and run sets too), the same in any context; the entry records it, and a Rust host on a
partition of `P` SMs takes only pins chosen for it with `Manifest::with_sm_partition(Some(P))` (`docs/manifest-schema-3.md`, section 9.3).

**A pinned cuDNN convolution.** `impl="cudnn.conv_fwd"` declares a forward convolution by its signature, `(x, w) -> y` in the order of `layout`
(`"NCHW"`, the default: `x [N, C, *S]`, `w [K, C/G, *R]`; `"NHWC"`: `x [N, *S, C]`, `w [K, *R, C/G]`) with one to three spatial axes, f16, bf16 or f32
data, an f32 accumulator and one rounding, and pins what cuDNN runs for every bucket:

```python
T = Dim("T", buckets=[64, 646])

# the backend API (the default): an engine configuration, an engine and its knobs, chosen as torch chooses it
@tilefish.library("conv", impl="cudnn.conv_fwd", layout="NHWC", padding=3)
def conv(x: Tensor[1, T, 64, f16], w: Tensor[64, 7, 64, f16]) -> Tensor[1, T, 64, f16]: ...

# the legacy API: the algorithm enum of cudnnConvolutionForward, cudnnGetConvolutionForwardAlgorithm_v7's first deterministic answer that fits
@tilefish.library("down", impl="cudnn.conv_fwd", layout="NHWC", stride=2, padding=1, api="legacy")
def down(x: Tensor[1, T, 64, f16], w: Tensor[128, 4, 64, f16]) -> Tensor[1, tilefish.cdiv(T, 2), 128, f16]: ...
```

The declared result must be the convolution's output at every bucket (`(S + 2 * padding - dilation * (R - 1) - 1) // stride + 1`; `cdiv(T, 2)` is that
here). The math is part of the declaration: `"tensor_op"` (the default of 16-bit data) or `"fma"`, and for f32 data `"fma"` (TF32 off) or `"tf32"`, said
explicitly. `api="backend"` pins an engine configuration (the engine's global index and every knob choice: it names a kernel) under `heuristic="instant"`,
torch 2.9's posture with `deterministic = True` and `benchmark = False` (`CUDNN_HEUR_MODE_INSTANT`, then the fallback list, filtered for determinism, no
down-conversion and, for `"fma"`, no tensor cores), or `"mode_b"`; `api="legacy"` pins the algorithm enum. `algos=tilefish.CudnnTable(arch, sm_count,
cudnn_version, {(n, c, k, input, filter, stride, padding, dilation, groups): pin})` imports pins instead. The entry records the problem, the math, the pin,
how it was chosen, the cuDNN version (`cudnnGetVersion()`), the SM count and an `sm_count_target`; `replay` and the Rust host refuse another cuDNN version,
another SM count and a process with `NVIDIA_TF32_OVERRIDE` set (it changes what cuDNN picks behind the declared math), and vet the pin (a deterministic answer
of `cudnnGetConvolutionForwardAlgorithm_v7`; an engine of allowed notes whose knobs are in range and whose plan finalizes). Since two builds of one cuDNN
version answer the same `cudnnGetVersion()`, `export` also records a canary per entry, the digest of the pin's output on operands made of a seed (both
made on the device by one PTX module in both hosts: a plan set of 743 entries loads in 1 to 2 s), which `replay` and the Rust host run again (once,
on a stream of their own, never the NULL stream) and refuse when the digest differs; an entry without one loads as before. A knob of -1 in an imported pin
is cuDNN's "not set" and is left out. Every call sets cuDNN's stream to the one it is given. There is no bias (torch's cuDNN convolution adds it with a separate `add_`, as a tilefish
kernel does).

The `"instant"` pin is `torch.nn.functional.conv1d` / `conv2d` / `conv3d`'s bytes where torch runs cuDNN (`test_gpu_conv.py`: 15 problems, three operand sets,
1-D, 2-D and 3-D, f16, bf16 and f32 with TF32 off, strides, dilations, groups; a B300 MIG slice with cuDNN 9.10.2 and 9.13.0, an RTX 5090 with 9.13.0),
and a legacy pin of
`IMPLICIT_PRECOMP_GEMM` is torch's legacy path's. Both APIs run in launch plans (the workspace is the arena's) and capture in CUDA graphs; the binding is
ctypes on the `libcudnn` the process has (torch's), and the Rust crate loads cuDNN only for a manifest that has a convolution (`Manifest::conv`, `Conv`). See
`docs/manifest-schema-3.md`, section 9.4.

## Masks, indices, gathers and copies

A lowered `@kernel` also compares, selects, counts positions, reduces to an index, and gathers and scatters rows at indices that are device
data; a graph materialises a view or the patches of a convolution. Each has an exact numerics contract (notes 7 to 11 of `tilefish.lower`) and
runs in `jit`, `replay` and `reference`, alone and in a plan.

```python
import tilefish
from tilefish import Dim, DevScalar, Tensor, bf16, f32, i32, i64

V, R, C = Dim("V"), Dim("R"), Dim("C", 3000)
D = Dim("D", 1024)

@tilefish.kernel
def embed(table: Tensor[V, D, bf16], ids: Tensor[R, i64], n: DevScalar[i32]) -> Tensor[R, D, bf16]:
    rows = tilefish.gather_rows(table, ids, oob="zero")               # an index outside [0, V) loads a row of +0.0
    keep = tilefish.iota(rows, axis=0) < tilefish.load(n)            # a mask: the rows below a device-scalar count
    return tilefish.where(keep, rows, (rows.to(f32) * 0.0).to(bf16))  # a select: the kept rows' bits as they are

@tilefish.kernel
def greedy(logits: Tensor[R, C, bf16]) -> Tensor[R, i64]:
    return tilefish.argmax(logits, dtype=i64)                        # torch's rule: the first NaN, else the first maximum
```

- `== != < <= > >=` give a mask (`tilefish.bool_`, a value inside the body: store it with `.to(u8)`); masks combine with `& | ^ ~`; a scalar is
  rounded to the operand's dtype before it is compared. `tilefish.where(m, a, b)` selects bits, NaN payloads and signed zeros included.
- `tilefish.iota(x, axis)` is the index along an axis (`[R, 1]` for the rows of `[R, D]`, `[D]` for its columns); `//` and `%` of integers by a
  positive constant have Python's semantics.
- `tilefish.argmax` / `argmin(x, dtype=i32 | i64)` along the last axis are exact and independent of the reduction tree (a combine of
  (value, index) pairs); a row of up to 16384 columns is walked in chunks of 1024.
- `tilefish.gather_rows(x, idx, oob="zero" | "clamp")` and `tilefish.scatter_rows(dst, idx, src, oob="skip")` copy rows (or elements) as raw
  bits, with the out-of-range policy declared at the call.
- `x.to(i32, rounding="rn" | "rz" | "rd" | "ru", saturate=True | False)` (also `i64` and `u8`): a float to integer cast says how it rounds
  (to nearest even, toward zero, down, up; there is no default) and what a value out of range becomes: clamped to the type's range with a NaN
  0 (`saturate=True`, the default, Rust's `as`), or the low bits of the `i64` (`saturate=False`: C's narrowing, torch's cast to `u8`). Each is inline PTX
  (`cvt.rni.s32.f32` and the like) and is byte-identical to the reference on every one of the 2**32 f32 bit patterns (note 18).
- In the row template, `x[k]` of a read-only parameter is read at its offset: `codes[k]` of a `[K, R]` codes plane is a per-row operand (the
  index of `gather_rows`), `tables[k]` of a `[K, N, D]` parameter a table, with the dimensions of the offset runtime scalars (note 19).
- `x.to(bf16, nan="preserve")` keeps a NaN's sign and payload (the default, `"canonical"`, gives `0x7FFF`); `tilefish.sin`, `tilefish.cos` and
  `tilefish.tanh` are libdevice's (`sinf`, `cosf`, `tanhf`), built with flush-to-zero like every libdevice function Triton links: over every f32,
  torch's CUDA bits but `sin` and `tanh` of a subnormal, which are a zero of its sign (notes 10 and 14).
- **IEEE math.** `@tilefish.kernel(math="ieee")`, or `math="ieee"` at one op (`tilefish.div(a, b, math="ieee")`, `tilefish.exp(x, math="ieee")`),
  makes the f32 math CUDA C++'s without fast math and without flush to zero, what torch's CUDA kernels are built with: `/` and `sqrt` are IEEE 754
  (`div.rn.f32`, `sqrt.rn.f32`; a constant divisor is divided by), `exp` is `expf`, `silu` torch's `x / (1 + expf(-x))`, `rsqrt` `rsqrtf`, and `sin`
  and `tanh` keep a subnormal, each written out as the inline PTX nvcc emits (Triton links libdevice with flush to zero). On every one of the 2**32 f32 bit
  patterns these are torch's CUDA bits, and `/` is torch's division of tensors; with `fp_fusion=False` too, a body of these ops is torch's eager
  composition of the same ops byte for byte. The default, `math="fast"`, is the contract of before (note 13 of `tilefish.lower`).
- **Primitives for reproducing a CUDA kernel.** `tilefish.erf(x, math="ieee")` is CUDA's `erff` without flush to zero (the default math's is
  libdevice's, `gelu`'s); `tilefish.sin_approx(x)` is `__sinf` (`sin.approx.f32`), `tilefish.rcp(x)` `__frcp_rn` (`rcp.rn.f32`),
  `tilefish.fma(a, b, c)` `fmaf` (one rounding, whatever `fp_fusion` says), and `-x` (`tilefish.neg`) is CUDA's negation, `-0.0` for `+0.0`
  where Triton's `-x` is `0 - x` and the canonical NaN for every NaN (written out, so that a negation ptxas folds into a select keeps it). Each
  is the bits of the CUDA C++ function on every f32, measured against NVRTC on the GPU (notes 15 and 16).
- **The CUDA math guard.** `expf`, `erff`, `tanhf` and the other functions those ops copy are not the same in every CUDA release (CUDA 13.2
  changed `erff`). The manifest entry of a generated kernel records the functions it uses, the releases tilefish measured each on, and the
  libdevice it linked (`cuda_math`); a run warns (`TilefishCudaMathWarning`) where torch is built with another release or a replay's process would
  link another libdevice, and the Rust host refuses a release with `Manifest::check_cuda_math`. `docs/numerics.md` has the table and the procedure
  to run on a CUDA or torch change (`pytest -m cuda_math`).
- **Ordered sums.** `tilefish.sum(x, axis=-1, order=...)` adds in the order a CUDA kernel does: `order="sequential"` is one thread's loop from
  `+0.0`, `tilefish.tree(256)` is 256 threads over strided columns and a shared-memory halving tree, and
  `tilefish.tree(128, offsets=(16, 8, 4, 2, 1, 64, 32), vector=8)` is 128 threads of 8 consecutive columns, a warp-shuffle tree and then the
  warps; `fma=True` makes each step of a chain `acc = fma(a, b, acc)` for `tilefish.sum(a * b, ...)`, as nvcc compiles `acc += a * b`. The bytes
  are those kernels' and the same at every `num_warps` (note 17):

  ```python
  @tilefish.kernel(math="ieee")
  def rmsnorm(x: Tensor[R, 1024, bf16], w: Tensor[1024, bf16]) -> Tensor[R, 1024, bf16]:
      v = x.to(f32)
      ss = tilefish.sum(v * v, -1, keepdims=True, order=tilefish.tree(128, offsets=(16, 8, 4, 2, 1, 64, 32), vector=8), fma=True)
      return ((v * tilefish.rsqrt(ss / 1024.0 + 1e-6)) * w.to(f32)).to(bf16)   # a 128-thread CUDA rmsnorm, byte for byte
  ```
- The elementwise template broadcasts an operand over the leading axes (a `[T, D]` table added to a `[K, T, D]` batch), and along any axis by
  numpy's rules (a `[H, 1, L]` mask of the keys over `[H, L, L]` scores, a `[K, T, 1]` scale per row): such an operand is read at the offset of the
  lane's coordinates, and `tilefish.iota(x, axis)` is the lane's coordinate along any axis (a causal mask is `iota(s, 2) <= iota(s, 1)`). The sizes the
  coordinates need are runtime scalars of the dimensions, so one binary serves every size (note 12).
- In a graph, `tilefish.contiguous(view)` and `tilefish.im2col(x, kernel, stride, padding)` are ops whose Triton tilefish generates, reading
  a strided view: a materialised permutation, and convolution patches with channel-major columns and `+0.0` padding.
  `tilefish.im2col1d(x, kernel, stride=, dilation=, padding=, order="channel" | "tap")` gives the patches of a 1-D convolution of `[N, C, L]` as
  `[N, Lo, C * K]`, with a dilation, a padding `(left, right)` (a causal one is `(dilation * (K - 1), 0)`) and the columns channel-major or tap-major.
- `tilefish.col2im1d(cols, kernel, stride=, dilation=, padding=, output_padding=, order="channel" | "tap", bias=, layout="ncl" | "nlc")` is the
  overlap-add of a 1-D transposed convolution: `cols: [N, Li, C * K]` (any strides: a GEMM's `x^T @ W.reshape(C_in, C * K)` reshaped, as it is)
  becomes `[N, C, Lo]` or a channel-last `[N, Lo, C]`, `Lo = (Li - 1) * stride - left - right + dilation * (K - 1) + output_padding + 1`
  (torch's `conv_transpose1d(padding=p, output_padding=op)` is `padding=(p, p), output_padding=op`). Unlike the copies it adds, so the order of
  the adds is the contract, and it is the order of ATen's CUDA `col2im` (`F.fold` on CUDA): an f32 sum from `+0.0` over the input positions in
  ascending order (the taps descending), one rounding per add and nothing contracted (`enable_fp_fusion=False`), then the bias in f32, then one
  rounding to the dtype of `cols`. Three terms or more added in another order round differently, so this order is what makes the bytes
  `F.fold`'s: measured byte for byte against `F.fold` on CUDA in f32, bf16 and f16, and against `conv_transpose1d` on small integers, where every
  order is exact.

## Launch plans: a graph as a static list of launches over one arena

A model forward is not one kernel. `tilefish.plan(graph, buckets=...)` compiles a `@tilefish.graph` into a **launch plan**: for every combination of the bucket values of its
dimensions, the ordered launches of manifest entries (a lowered kernel, a hand-written Triton extern, a prebuilt binary or a pinned cuBLASLt GEMM), with every pointer argument bound to a
buffer or to a *view* of one (a `reshape`, `permute`, `select` or `split` copies nothing), and **one arena of device memory** for everything the caller does not provide: the intermediates, one
slot per `DevScalar` input and the cuBLASLt workspace. Every arena buffer has a fixed byte offset, a multiple of 256, **the same in every bucket** (the arena is sized for the largest), so a plan
can be captured in a CUDA graph once per bucket at fixed addresses. The steps run on one stream in the order of the IR, with no synchronization between them and none implied (an in-place call
keeps the storage of the version it consumes). `reuse=True` lets intermediates share bytes where no step uses both: the transformer block of the gate (rmsnorm, a bias GEMM whose output is split
into q, k and v views, an attention that masks the keys at a device scalar `n`, a GEMM, a residual add and rmsnorm, two GEMMs around a gelu, a residual add; rows bucketed over 32, 64 and 128)
needs 9 634 048 bytes without reuse (8 519 680 of them the workspace) and 9 240 832 with it; unrolled 24 times (216 launches per bucket, the weights of the layers views of stacked
parameters) the arena is 36 765 952 bytes without reuse and 9 306 368 with it, one layer's intermediates plus the workspace whatever the depth.

```python
plan = tilefish.plan(block, buckets={"M": [32, 64, 128]}, reuse=False)       # no GPU, no torch: steps, buffers, offsets
p = tilefish.runtime.export(block, "build/")                                  # binaries, manifest.json and plan.json (schema "tilefish.plan.v1"); p.digest is the pin
y = tilefish.run(block, x, n, *weights)                                       # jit: the same plan, binaries built in memory
y = tilefish.run(block, x, n, *weights, mode="replay", plan="build/", pin=p.digest)   # a verified plan directory, or trust_directory=True
y = tilefish.run(block, x, n, *weights, mode="reference")                     # each op's reference composed in torch
cap = tilefish.capture(block, x, *weights, devscalars={"n": n}, outputs=y)    # the plan in a CUDA graph of its own
cap.set_devscalar("n", 17); cap.replay()                                      # a replay ordered with every run of the plan, from any thread
```

`plan.json` carries the plan and the digest of the manifest it was built against, so **pinning the plan digest pins every binary and every pinned GEMM algorithm it launches**. A replay loads and
verifies the file and its manifest (a tampered plan, a wrong pin, a plan built against another manifest, and a plan of a graph that changed are all refused), allocates the arena once per device
and keeps it, and checks **every step's preconditions before the first launch**: a failure launches nothing, not even the write of a device scalar. A run allocates nothing but its outputs
(`outputs=` gives them) and waits for nothing: the GEMM workspace is in the arena, a device scalar is written by a stream-ordered copy. So **a replay under `torch.cuda.graph` captures and the
graph replays byte-identically** (`runtime.prepare` does the allocating and the loading that cannot happen inside a capture; `docs/plan-schema-1.md` lists every reason a plan could fail to
capture). Every run of a plan on a device uses the one arena, so **runs of one plan on several streams (or threads) are ordered on the device** by an event of the arena: a run waits on its
stream for the run before it and records the event after its last launch, so they never overlap and their results are correct, at the cost of running one after the other
(a run on the stream of the event's last record skips the wait: runs that stay on one stream cost one `cuEventRecord` each).
Runs that must run concurrently need an arena each: `lane = tilefish.runtime.share_arena([graph], name="lane1")` is another arena of the same plan
(its own memory, lock and event; `lane.run(graph, x)` on its stream does not wait for the runs on the first), one per stream (Rust: one instantiation per lane).
`tilefish.capture(graph, *inputs, devscalars=..., outputs=...)` captures the plan in a CUDA graph of its own: its `replay()` takes the arena's lock and waits for and records that event
around the graph, as a run does, so **its replays are ordered with every run and replay of the plan, from any thread and on any stream**, and `set_devscalar` changes a device scalar for
the next replays with no synchronization. A plan run inside your own `torch.cuda.graph(...)` captures too: the wait and the record are external event nodes of the graph, so its arena is
the plan's arena and its replays are ordered with the runs whose record they see. But torch's `replay()` takes no lock: **a raw graph replayed while another thread is in the middle of a run
of the same plan overlaps that run** (wrong bytes, no error), so order the two yourself, replay with `tilefish.runtime.replay_graph(g)` (which takes the arena's lock around `g.replay()`), or use
`tilefish.capture`. The second thread that uses an arena such a graph holds gets a `TilefishOrderWarning` (an error with `warnings.simplefilter("error", tilefish.TilefishOrderWarning)`).
`jit` and `replay` are one code path over binaries from two places, so they are identical by construction, and the gate checks on a GPU that plan replay, plan jit and the per-op
eager composition of the same ops give the same bytes for every bucket and two values of `n`.

**An `Out` written over its input.** A hand-written kernel `k(x, r, y, r_out)` that reads every element of `r` before it writes the same element of `r_out`
declares `r_out: Out[Tensor[M, D, f32], MayAlias("r")]`: a launch (Python or Rust) then accepts `r_out` and `r` that are exactly one tensor and refuses any
other overlap, and a plan writes `r_out` over `r` when nothing reads that `r` after the call (a whole intermediate, no later reader, not returned), with no
buffer of its own; otherwise the result gets one, so the values are the same either way (manifest schema 3, section 5.4; `docs/plan-schema-1.md`, section 8).

**Copy steps.** `r = tilefish.copy(x)` in a graph is a step of kind `copy`: the dense bytes of `x` (a tensor, or a dense view such as `x[1]`) copied into a
buffer of its own with `cuMemcpyDtoDAsync`, a memcpy node in a CUDA graph. The copy is an intermediate an in-place call may update, where `x`, the caller's,
is never written. `state[...] = r` into an `InOut` parameter is a copy step into the caller's tensor. A copy of a view that is not dense is a launch of
`tilefish.contiguous` instead (a strided view of rank 1 to 4 into a dense tensor), as the
plan is made, and so is a store of one: `state[...] = t.permute(1, 0)` writes the transpose into the caller's tensor (`docs/plan-schema-1.md`, section 7.5).

**Memset steps.** `acc = tilefish.zeros_like(x)` (or `zeros_like(x, dtype=i32)`) in a graph is a step of kind `memset`: a buffer of its own whose bytes are
set to zero with `cuMemsetD8Async` (a memset node in a CUDA graph), which an in-place call may then accumulate into, or which the graph returns (the memset
writes your output). `state[...] = tilefish.zeros_like(state)` is one memset of your `InOut` tensor. No kernel has to zero a buffer any more
(`docs/plan-schema-1.md`, section 7.6).

**Returned views.** A graph may return a reshape of a result at no cost (`return y.reshape(M, N)` of a flat `y`: the caller's output is `y`'s buffer, in the
returned shape, and the step that writes it binds it through a flat view), and any other dense view, a parameter or a value twice, which a copy step after
the last call puts into the caller's output. A view that is not dense (a transpose, a column block) is materialised there by a launch of
`tilefish.contiguous`.

**Named outputs.** `@tilefish.graph(outputs=("y", "residual"))` names the returned values: the plan's output buffers have those names (else `out0`,
`out1`, ...), `tilefish.run(..., outputs={"y": y, "residual": r})` takes them by name, and the Rust host binds them by name; both hosts also take `out<i>` for
the `i`-th returned value, so a host written for the names of before keeps working.

**Inputs and weights.** `@tilefish.graph(inputs=("x",))` (or `weights=(...)`, or both) says which parameters a call gives every time and which a
host binds once, when it loads the model. The plan records the roles (`"roles": "declared"`), and both hosts bind the weights once:
`w = tilefish.runtime.bind_weights(graph, {"w1": t1, ...}, mode="replay", plan="build/", pin=p.digest)`, then `w.run(x)` and `w.capture(x, ...)`
(Rust: `PlanRun::bind_weights`, a `WeightedRun` whose `launch` and `capture` take the inputs only). Without the declaration a plan labels a
parameter by its shape, as before (`weight` when it mentions no dimension: every parameter of a fully static graph), and `bind_weights` refuses it.

**Plan sets.** A stage whose launch count depends on a key is one plan per key; `tilefish.runtime.export([g1, g2, ...], "build/")` exports them as a
*plan set*: one manifest (each binary once, whichever plans launch it), `<graph>.plan.json` per graph and `plans.json`, an index whose digest pins every
plan, their manifest and every binary. A replay takes `plan="build/"` and the set's digest or the plan's; Rust `PlanSet::load(dir, pin)` and
`set.plan("g2")` (the plans share the manifest and its loaded modules). `docs/plan-schema-1.md`, section 15, says why a set and not a repeated step range.

**An arena shared by the plans of a set.** A host that runs plans of a set one at a time (a request's stage A, then B, then C) can give them one
arena: `s = tilefish.runtime.share_arena([a, b, c], mode="replay", plan="build/", pin=planset.digest)`, then `s.run(a, x)`, `s.capture(b, ...)`,
`s.bind_weights(c, {...})`. The arena has the bytes of the largest plan's arena (the gate's transformer block cut into three stages: 9 109 504 bytes
instead of 26 476 800), each plan's buffers at their own offsets in it, so the documents and their pins are unchanged and every plan captures at
fixed addresses. Every run, capture and replay of any of the plans is ordered with all the others (one lock, one order event), so two of them never
overlap on the device; nothing in the plans' own regions outlives a run, and a tensor of yours anywhere in the arena is refused. Rust:
`set.instantiate(&stream, &["a", "b", "c"])`, a `SetRun` of `PlanRun`s on one `SharedArena`. `share_arena(..., name="lane1")` is another arena of the
same plans, for a lane that runs concurrently. `docs/plan-schema-1.md`, section 15.1.

**Carried buffers.** A stage can hand an intermediate to the next with no tensor of yours: `@tilefish.graph(carried=("h",))` on both graphs makes the
parameter `h` a buffer the arena holds (role `carried`), in a region after the plans' own regions, the same for every plan of the arena that names it.
`stage_a(x, h: InOut[...])` writes it (`h[...] = encode(x)`: the launch of `encode` writes the arena's `h` directly), `stage_b(h)` reads it, and a run gives
every parameter but the carried ones: `s.run(stage_a, x)`, then `s.run(stage_b)`, whose sizes are the ones `h` was written with. A run that reads `h` before
any run on the arena wrote it, or in another shape, is refused before anything is enqueued; the captures of `tilefish.capture` check and note `h` at every
replay. Both hosts compute the same layout from the documents, which the pins cover (`docs/plan-schema-1.md`, section 15.2).

**Debug taps.** `tilefish.run(graph, ..., taps={"t3": t, ("t5", 4): u})` copies buffers of the plan into your tensors right after a step (by default the
last one that writes the buffer), before a later step may reuse their bytes: the intermediates of the very plan a product runs, with the plan and its digest
unchanged (`plan.shape_of("t3", M=64)` gives the shape; `tilefish.capture` takes `taps=` too; Rust: `PlanRun::launch_tapped`, and
`PlanRun::capture_tapped`, whose replays copy the taps again).

**One step alone.** `tilefish.runtime.run_step(graph, 3, {"t2": a, "w_o": w, "t3": o}, mode="replay", plan="build/", pin=p.digest)` launches one step of the
plan on your tensors, with the binary and the binding of its arguments that the pinned plan says (Rust: `PlanRun::launch_step`): one op of an exported plan
replayed on a reference's inputs, under the pin a product uses.

A plan launches declared operators, views and the arithmetic of the body as fused regions (next section). An `Out` parameter, a call to another graph, an in-place call on a view
and a view read after its tensor was updated in place are refused with the rule that says so. `docs/plan-schema-1.md` specifies the file exactly (every field, the validation
rules, the digest) for the host that will run it without Python.

## Fusion: arithmetic in a graph body

A graph body may compute. The arithmetic between two calls (`silu(g.to(f32)) * u.to(f32)` between two GEMMs, a bias and an activation, a residual add, a mask
from a device scalar, a dequantisation) is traced like a kernel body, with its rules (no implicit promotion, a scalar rounded to the tensor's dtype, f32 math
functions), and the planner groups it into **regions**: each a `@tilefish.kernel` of its own that tilefish generates (named `fused_<hash>` by its content, lowered
by the same templates), and one ordinary kernel step of the plan. Neither schema and neither host changes (`docs/rfcs/0001-plan-fusion.md`).

```python
@tilefish.graph(inputs=("x",))
def mlp(x: Tensor[M, H, bf16], w_gu: Tensor[2 * F, H, bf16], w_d: Tensor[H, F, bf16]):
    g, u = gemm_gu(x, w_gu).split(F, axis=-1)
    a = (tilefish.silu(g.to(f32)) * u.to(f32)).to(bf16)      # one kernel, not five
    return gemm_d(a, w_d)
```

**Fusion never changes bytes.** A fused plan writes the bytes of its *unfused composition*: every op a kernel of its own, every intermediate stored in the dtype the
IR gives it (`tilefish.fusion(grouping="none")` is that plan, and its taps show every intermediate). A region kernel contracts nothing (`fp_fusion=False`), and its code
does not depend on its neighbours (note 20 of `tilefish.lower`; the code of every kernel with `fp_fusion=False`, note 2): every float `+ - *` is one scalar `.rn`
instruction of inline PTX, because LLVM packs two lanes' f32 ops into `mul.rn.f32x2` / `add.rn.f32x2` and ptxas 12.9 contracts that pair (into `FFMA2` on sm_100 and
sm_103, `FFMA` on sm_120) even with `--fmad=false`; every narrowing float cast is inline PTX, because the folds of MLIR and LLVM keep an input NaN's payload through
`x.to(f32).to(bf16)` in one kernel; and a negation gives the canonical NaN explicitly, as in every kernel, because ptxas folds `neg.f32` into a select as a sign flip.
A reduction is a kernel of its own (a Triton tree reduction adds in another tree when other loads share its kernel:
357 to 399 of 1024 rows differed, measured); an op whose value nothing reads is not computed. One rounding of `a * b + c` is asked for with `tilefish.fma`.

**Checked at every export.** `export` runs every region of more than one op against its ops one by one, `jit` on the device, at every bucket, on seeded inputs that
reach every corner (NaNs with payloads, infinities, subnormals, signed zeros), and refuses the export at a difference (`verify=False` opts out; on a device of
another architecture the check is skipped with a `TilefishFusionWarning`). It writes `<graph>.fusion.json` next to the plan, the **fusion report**: for every
region the ops of the body it took, what it reads (where it is, or a copy), what it writes, every rounding it
keeps and the rewrites of the mode; `tilefish.fusion_report(graph)` and `tilefish.verify_fusion(graph)` give the same on demand. A view that is not
dense (the halves above, a head, a transpose) is read where it is, a stride per axis, by a region of the elementwise template, and copied by
`tilefish.contiguous` first for a region of the row template. The tests hold fused to unfused
on every bf16 and f16 bit pattern, on grids of 2**22 bit patterns, on 120 random graphs of up to 24 ops, and the inline casts to `.to()` on every f32.

**The mode** is declared, `@tilefish.graph(fusion=tilefish.fusion(...))`, and every choice is exact (the region's source carries it, so the pin does):

| parameter | values (default first) | what it says |
|---|---|---|
| `version` | `1` | the grouping rules, limits and rewrites, frozen |
| `grouping` | `"auto"`, `"none"` | regions as large as the rules allow (a region never spans a call, at most 64 ops), or one kernel per op |
| `math` | `"fast"`, `"ieee"` | the default math of the body's f32 ops; an op's own `math=` wins |
| `intermediates` | `"declared"`, `"opmath"` | every op rounds to its IR dtype; or torch's eager rule for a bf16 or f16 `+ - *` with a python scalar (computed in f32 with the scalar in f32, rounded once): with `math="ieee"` the bits are torch's eager composition (every non-NaN value, checked on every bit pattern) |
| `fp_contract` | `"none"`, `"mul-add"` | nothing contracted; or an f32 `a * b + c` (or `- c`) whose product nothing else reads becomes `tilefish.fma`, one rounding |
| `verify` | `True`, `False` | whether `export` checks the regions |

Each rewrite is made on the IR before the regions are formed, so its rounding points never depend on where the regions fall. `tilefish.barrier(x)` makes `x` a
boundary of the regions (it gets a buffer of the plan, which `taps=` reads); it never changes a byte. Not yet planned: a scatter in a graph body, a reduction joined to
a region (it runs alone), a view read where it is by a row region (it is copied first), modes that are not exact (`docs/rfcs/0001-plan-fusion.md`,
section 11).

## The Rust host

The `tilefish` crate (`crates/tilefish`, version 0.0.1) is the
host of a manifest directory, without Python or Triton: it reads the manifest as
strict JSON, recomputes the digests exactly as Python does (the `sha256` of each
cubin, the `sha256_code` of its machine code, and the digest of the whole
manifest) and refuses a directory whose digest is not the pin it is given
(`Pin::Digest`; `Pin::TrustDirectory` is explicit). It builds on cudarc's safe
layer and calls the driver directly nowhere: `Manifest::kernel(&ctx, ...)` loads a
cubin into a `CudaContext` that the kernel then keeps alive, and the kernel
launches on a cudarc `CudaStream` (`Kernel::launch`, safe: the stream is checked
to be of the kernel's context) or, with the `unsafe` `Kernel::launch_raw`, on a
raw `CUstream` (it makes the kernel's context current for the call and puts back
what was). A tensor is made of a cudarc `CudaSlice` or view (`from_cuda`: no
`unsafe`; it borrows the slice, so the slice cannot be freed under it, and making
it records nothing on the slice) or of a region the host vouches for (`unsafe
DevicePtr::from_raw`, which has a lifetime and no tracking). The launch gives a
slice to cudarc's launch builder on the stream it launches on, which orders it
after the slice's earlier writes, and makes the slice's own stream wait for the
kernel, so freeing the slice (or any later work on its stream) runs after the
kernel however many other streams read it; a kernel that writes a slice from
another stream first waits for everything enqueued on the slice's own stream, so
it runs after all earlier readers. (A reader after a writer on another stream is
cudarc's own tracking, which needs a context that has made a stream of its own;
an `Err` from a launch does not promise that nothing was launched, and the crate
orders the free behind a kernel that may have run.) A CUDA graph is captured
with `launch_raw` (or `launch`) and regions: the graph holds the addresses and
nothing that keeps the memory alive, so it must not be replayed after the memory
is gone, and a launch of slices on a capturing stream is an error, not a graph,
whatever the cudarc context. The loaded function's parameter sizes are compared
with the ABI of the manifest (`cuFuncGetParamInfo`, as Python's `replay` does), and
a cubin whose ELF header names another architecture than its entry is refused.
`cudarc` panics when there is no NVIDIA driver, so `tilefish::driver_available()`
says first.

A manifest (schema 3) carries what a host needs to check a launch on its own:
every pointer parameter records its declared shape, with static axes as sizes
(`["Rows", 1024]`), and every entry the constraints of its named dimensions
(`divisible_by`, `buckets`, and the bucket the binary is built for). A launch
takes nothing but its tensors. The crate binds the dimensions from their sizes
(and the stride dimensions of a strided view from its canonical strides; the
tensors the kernel reads first, then an `Out` tensor for a dimension only it has),
checks that they agree across arguments and with the static sizes, the exact
bucket and `divisible_by`, the dtype and rank of each tensor (a device scalar is
one element), `max_elements` and, for a view, `max_extent`, that the runtime
scalars (derived from the dimensions, from the element count of the tensor they
count, or from a stride) fit the 32 or 64 bits they are passed as, aliasing, the
alignment each pointer promises (16 bytes, or a strided pointer's element size),
contiguity of a tensor given for a parameter that is not strided, and the grid
against the device's limits, and evaluates the grid from its expression. There is
no way to tell a launch what a dimension is. A manifest of an older schema is
refused by both hosts: export it again.

**Schema 3 and the crate.** The crate reads manifest schema 3
(`docs/manifest-schema-3.md`) in full and launches everything it describes:
Triton kernels and prebuilt PTX and cubin binaries (exactly their parameters, no
scratch slots, `fixed` arguments at their slots), strided views
(`TensorRef::from_cuda_strided`, or over a region with `new_strided`; any element
strides and any offset), device scalars (a tensor of shape `[]` or `[1]`), `i64`
strides, and the pinned cuBLASLt GEMMs of the `library` section
(`Manifest::gemm`, `Gemm::launch`, and `unsafe Gemm::launch_raw` for a CUDA
graph). A GEMM runs the 64-byte algorithm the manifest pinned through cudarc's
`cublaslt::result`: it is refused when the process has another cuBLASLt than the
one that chose it, when the algorithm is not one cuBLASLt would have produced,
and when the library does not approve it for the problem. Its workspace is the
caller's last tensor (`Gemm::alloc_workspace` allocates the size the entry says),
so a launch allocates nothing and can be captured; the slices of a GEMM are
ordered like a kernel's. The published crate 0.0.1 reads schema 2 only. `emit`
writes typed launchers for all of it; the committed fixtures of the crate are
schema 3 manifests.

```python
from tilefish.hosts import rust
rust.emit(m, "launchers.rs")   # m = tilefish.runtime.export(...); ops=[...] cross-checks the declarations
rust.emit("build/", "launchers.rs", pin=m.digest)   # a directory is read only with its pin
```

`emit` takes a pinned manifest (the one `export` returns, `Manifest.load(path, pin=...)`,
or a directory with `pin=`: the file it writes is compiled and run, so a manifest
nobody vouched for does not write it, and every field that reaches it is
validated) and writes one Rust module with a struct per binary (per bucket), whose
`launch` takes typed tensors (`TensorRef<'a, Bf16>`, `TensorMut<'a, F32>`: the
borrow of a cudarc slice, or a region of device memory with its length that the
host vouches for with `unsafe DevicePtr::from_raw`; a shape that needs more bytes
than the memory has is refused, and so is a launch on a stream of another context
or of a tensor of another context) and documents the binary: its tensors, its
dimensions and their constraints, what is compiled in. It also embeds the digest
of the manifest it was generated from and refuses any other, and with
`embed=True` the manifest and the cubins as well. The output is deterministic.
`ops=` is optional: each declaration it lists must be exactly what the manifest's
entry says, and gives the docs the tilefish signature.

The byte-identity gate (`python/tests/rust_gate.py` with
`crates/tilefish/tests/gpu_gate.rs`) checks on a GPU that the Rust host and
`replay` agree byte for byte, on a fresh export and with the manifest directory
and with the embedded manifest, for the five goldens, a bucketed row kernel over
each bucket, the hand-written kernels (outputs and in-place tensors), a `tl.dot`
kernel that needs more than 48 KiB of dynamic shared memory, strided views
(a fused qkv, any element offset, aligned and not, transposed and expanded
views, 64-bit strides), device scalars, prebuilt PTX and cubin binaries (the PTX
of a Triton build and hand-written PTX with `fixed` arguments) and the pinned
cuBLASLt GEMMs with and without a bias at every bucket; it also checks the
refusals of schema 3, a strided kernel and a GEMM captured in a CUDA graph, and
the order of the frees of their slices against other streams. On any machine,
`cargo test` and `pytest` check that the digests Rust computes from a committed
manifest directory (`sm_103`, and a cross-compiled `sm_120` one) are the ones
Python computes, that Rust decides the same as Python on a thousand calls, and
that Rust refuses what Python refuses.

## The C++ host

`crates/tilefish-capi` is the C ABI of the Rust host: `libtilefish_capi` (a
shared and a static library) and `tilefish.h`, which cbindgen generates from the
crate and a test keeps current, with a header-only C++17 wrapper, `tilefish.hpp`.
Every load, verification, check and launch is the `tilefish` crate's: there is
no second implementation, so a C++ host refuses what the Rust host refuses and
runs the same machine code (`docs/rfcs/0002-cpp-host.md`). No manifest or plan
schema changes.

```sh
cmake -S crates/tilefish-capi -B build && cmake --build build   # cargo builds the library
ctest --test-dir build                                         # C99 and C++17 tests, no GPU needed
cmake --install build --prefix /opt/tilefish                   # find_package(tilefish): tilefish::tilefish, tilefish::tilefish_static
```

```cpp
#include "tilefish.hpp"

auto ctx = tilefish::Context::primary(0);   // the device's primary context: the CUDA runtime API's
auto manifest = tilefish::Manifest::load("build/", "<the manifest's digest>");
auto kernel = manifest.kernel(ctx, "gelu_erf");
tilefish::Region x{x_ptr, x_bytes, 0}, y{y_ptr, y_bytes, 0};   // device memory the host owns
kernel.launch(stream, {tilefish::TensorRef<tilefish::Bf16>(x, {4096}), tilefish::TensorMut<tilefish::Bf16>(y, {4096})});

auto run = tilefish::LaunchPlan::load("build/", "<the plan's digest>").instantiate(ctx, stream);
run.launch(stream, {{"x", xt}, {"out0", yt}}, {{"n", 64}});
auto graph = run.capture(stream, {{"x", xt}, {"out0", yt}}, {{"n", 64}});
graph.replay(stream);
```

`tilefish.hosts.cpp` writes typed launchers and plan runners, as
`tilefish.hosts.rust` does, from a pinned manifest or plan only, with every
field validated: one class per binary, GEMM and convolution, whose `load`
refuses a manifest of another digest and whose `launch` takes one typed tensor
per parameter (a `bf16` tensor cannot be given where an `f32` one is declared),
and one class per graph with an `Externals` and a `Scalars` struct. With
`embed=True`, the manifest and its cubins go into a companion source file
(`launchers_embedded.cpp`) and `load_embedded()` verifies them with the pin.

```python
from tilefish.hosts import cpp
cpp.emit(m, "launchers.hpp", embed=True)          # m = tilefish.runtime.export(...), or a directory with pin=
cpp.emit_plan("build/", "runner.hpp", pin=plan_digest)
```

What the host owns, and how the boundary behaves:

- **Memory** is a region (`tilefish_tensor`, `tilefish::Region`): an address,
  a length and a device that the host vouches for, as for
  `DevicePtr::from_raw` in Rust; the host keeps it allocated until the launches
  that use it are done (for a captured plan, until it is destroyed) and orders
  it against its other streams. Everything else is checked before anything is
  enqueued, the tensor fitting its region included.
- **Contexts and streams** are the host's. A context handle is a device's
  primary context, retained and released, or a context the host lends
  (`Context::borrow`, a green context's for example), which tilefish never
  destroys. A stream is a `CUstream`, the same type as `cudaStream_t`. Every call
  leaves the thread's current context as it found it.
- **CUDA graphs.** A single launch on a stream the host is capturing is captured
  like any kernel node. A plan is captured with `capture` (a plan launch on a
  capturing stream is refused): the captured plan owns its graph and orders the
  arena with every other run.
- **Errors** are a status per call (`TILEFISH_ERROR_*`: one per kind of error of
  the crate, and invalid arguments, no driver and a caught panic) with the
  thread's last error (`tilefish_last_error`: the message, the precondition, the
  `CUresult`); `tilefish.hpp` throws them as `tilefish::Error`. A program built
  without exceptions uses `tilefish.h`.
- **Threads.** Every handle may be used from several threads at once, except a
  captured plan (one thread at a time). Runs on several streams at once need an
  arena each.
- **cuBLASLt and cuDNN** are opened at run time by name (`LD_LIBRARY_PATH`, or a
  copy the host loaded first), as in Rust, and a pin made with another version is
  refused at load.
- **Versions.** `tilefish_abi_version()` and the header's `TILEFISH_ABI_MAJOR`
  and `TILEFISH_ABI_MINOR`: a minor version only adds functions and values, and
  `tilefish.hpp` refuses a library of another major version.

The C++ half of the byte-identity gate runs the cases of the Rust gate from the
same directory: `python rust_gate.py prepare WORK` also writes the C++
launchers and plan runners (the block's, and every fused plan's), `cmake -S crates/tilefish-capi -B build
-DTILEFISH_BUILD_GPU_GATE=ON -DTILEFISH_GATE_DIR=WORK` builds
`tilefish_cpp_gate` (`crates/tilefish-capi/tests/gpu/cpp_gate.cpp`: kernels,
GEMMs, convolutions, plans launched and replayed, fused plans, a shared arena,
carried buffers, weights bound once, refusals, graphs of single launches), and
`python rust_gate.py compare WORK --host cpp` holds what it wrote to Python's
replay byte for byte.

## Rewrites that know about rounding

Types make fusion legality mechanical: elementwise chains into GEMM
epilogues, a norm into the preceding residual add, quantization into the next
GEMM's prologue, permutations into strides instead of copy kernels, in-place
reuse of buffers. Bytes and FLOPs per operator follow from shapes and dtype
widths, so a build can report a roofline per kernel and count launches per
step.

Fusion can also change numerics. Every cast to a narrower type is a rounding
point in the IR, and rules come in two kinds:

- **exact**: every rounding point is kept and only kernel boundaries move.
  Applied automatically: the fusion of a graph body's arithmetic (above) is one.
- **numerics-changing**: a reduction order, an accumulator dtype or a rounding
  point changes. Applied only on request, and gated against the reference.

`num_warps` is part of a kernel's numerics identity in the same way: it fixes
the tree a `tl.sum` adds in, so the same kernel with another warp count differs
in the last bits. It is recorded in the declaration digest, the compile spec
and the manifest, and a replay refuses an entry that has another. Measured, it
is Triton's own reductions that depend on it; per-element ops, `argmax` and
sums with an `order=` have the same bytes at every warp count, so a kernel
whose every reduction has an order may change it for speed alone
(`docs/numerics.md`). So is FMA
contraction: a generated kernel always says whether `a * b + c` may be one
rounding (`@tilefish.kernel(fp_fusion=False)` says no), and a hand-written one
says it with `@tilefish.extern(triton=..., enable_fp_fusion=False)` (Triton's
compile option of that name; `None`, the default, leaves it to Triton). The
setting is in the declaration digest, every compile spec and the `options` of
the manifest entry, so a binary built with the other one is refused by a replay.
"No" is kept, not hoped for: the compile option alone does not hold on sm_100
and later, where LLVM packs two lanes' f32 operations and ptxas 12.9 contracts
the packed pair whatever `--fmad` says. So a generated kernel with
`fp_fusion=False` writes every float `+ - *` as one scalar `.rn` instruction,
and every binary built with `enable_fp_fusion=False`, a hand-written Triton or
Gluon kernel's included, is read back at build: one whose SASS has more fused
multiply-adds than the SASS of its PTX with the multiplies taken out is refused,
with the kernel's name and the fix (scalar `.rn` inline PTX for the roundings
that matter, or `enable_fp_fusion=True`; `docs/numerics.md`).

Whether a legal fusion is worth doing is still measured, not assumed. The
measurements live in the repository next to the rules.

## What tilefish is not

- **Not a kernel compiler.** Triton, CuTe DSL, cuTile, Helion and TileLang
  write kernels. tilefish types them, builds them and hosts them.
- **Not a serving runtime.** Scheduling, KV cache, batching and request
  handling stay in the host program. tilefish owns one forward step over
  buffers it has planned.
- **Not a promise to generate every kernel.** Hand-tuned attention and GEMMs
  enter as `extern` or library operators and keep their own numerics
  contract.

## Roadmap

- **V0: one real model, end to end.** The whole GPU forward of a production
  model of about 0.6B parameters (a convolutional front end, a bidirectional
  encoder and a causal GQA decoder) is written in tilefish. The generated Rust
  host replaces the hand-written launch code of an existing engine and
  reproduces its output byte for byte on every architecture it ships for.
  Starting from a naive version of the model, the rewrite rules rediscover the
  fusions that were made by hand. V0 needs typed signatures and manifests,
  `extern` for Triton functions and prebuilt PTX or cubins, strided views,
  device-side scalars, gather / scatter / im2col style index kernels, a static
  launch and memory plan per shape bucket, pinned GEMMs, and a numerics
  contract on every operator.
- **V1: quantization as types.** MXFP8, MXFP4 and NVFP4, with generated
  quantize and dequantize references and per-architecture scale layouts.
- **V2: more of the forward generated.** Row reductions and elementwise
  families lowered natively, and GEMM epilogue fusion through CUTLASS or
  CuTe DSL.
- **V3: C++ and Rust as first-class deploy targets**, with the Python
  frontend used only at build time.
