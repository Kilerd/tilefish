# 启动计划：把 graph 变成一个 arena 上的静态启动列表

[English](../../en/guide/plans.md) | **简体中文**

模型的一次前向不是一个 kernel（核函数）。`tilefish.plan(graph, buckets=...)` 把一个 `@tilefish.graph` 编译成 **launch plan（启动计划）**：对其各维度 bucket（分桶）取值的每种组合，给出 manifest（清单）条目的有序启动序列（一个下沉（lowering）生成的 kernel、一个手写的 Triton extern（外部 kernel）、一个预构建二进制文件，或一个已 pin（固定）的 cuBLASLt GEMM（通用矩阵乘）），每个指针参数都绑定到一个缓冲区或某个缓冲区的 *视图*（`reshape`、`permute`、`select` 或 `split` 不做任何拷贝），并为调用方没有提供的一切准备 **一个设备内存 arena（内存池）**：中间值、每个 `DevScalar` 输入一个槽位，以及 cuBLASLt 的 workspace（工作区）。arena 中每个缓冲区都有固定的字节偏移，是 256 的倍数，**在每个 bucket 中都相同**（arena 按最大的那个确定大小），因此一个 plan（计划）可以在固定地址上按每个 bucket 一次被 capture（捕获）进 CUDA graph（CUDA 图）。各步骤按 IR 的顺序在一个 stream 上运行，步骤之间没有同步，也不隐含同步（原地调用会沿用它所消费的那个版本的存储）。`reuse=True` 让没有任何步骤同时使用的中间值共享字节：门禁中的 transformer block（rmsnorm、一个输出被拆成 q、k、v 视图的带 bias GEMM、一个在设备标量 `n` 处屏蔽 key 的 attention、一个 GEMM、一次残差加和 rmsnorm、夹着一个 gelu 的两个 GEMM、一次残差加；行数按 32、64 和 128 分桶）不复用时需要 9 634 048 字节（其中 8 519 680 字节是 workspace），复用时需要 9 240 832 字节；展开 24 次后（每个 bucket 216 次启动，各层的权重是堆叠参数的视图），arena 不复用时为 36 765 952 字节，复用时为 9 306 368 字节：无论深度多少，都是一层的中间值加上 workspace。

```python
plan = tilefish.plan(block, buckets={"M": [32, 64, 128]}, reuse=False)       # no GPU, no torch: steps, buffers, offsets
p = tilefish.runtime.export(block, "build/")                                  # binaries, manifest.json and plan.json (schema "tilefish.plan.v1"); p.digest is the pin
y = tilefish.run(block, x, n, *weights)                                       # jit: the same plan, binaries built in memory
y = tilefish.run(block, x, n, *weights, mode="replay", plan="build/", pin=p.digest)   # a verified plan directory, or trust_directory=True
y = tilefish.run(block, x, n, *weights, mode="reference")                     # each op's reference composed in torch
cap = tilefish.capture(block, x, *weights, devscalars={"n": n}, outputs=y)    # the plan in a CUDA graph of its own
cap.set_devscalar("n", 17); cap.replay()                                      # a replay ordered with every run of the plan, from any thread
```

`plan.json` 带有 plan 以及构建它时所依据的 manifest 的 digest（摘要），因此 **pin 住 plan 的 digest，就 pin 住了它启动的每个二进制文件和每个已 pin 的 GEMM 算法**。replay（回放）会加载并校验该文件及其 manifest（被篡改的 plan、错误的 pin、依据另一个 manifest 构建的 plan，以及所属 graph（计算图）已经改变的 plan 都会被拒绝），在每个设备上分配一次 arena 并保留它，并且 **在第一次启动之前检查每个步骤的前置条件**：一旦失败，什么都不会启动，连设备标量的写入也不会发生。一次运行除了它的输出（由 `outputs=` 给出）之外什么都不分配，也不等待任何东西：GEMM 的 workspace 在 arena 中，设备标量由一次按 stream 排序的拷贝写入。因此 **在 `torch.cuda.graph` 下进行的 replay 可以被捕获，捕获得到的 graph 会逐字节一致地回放**（`runtime.prepare` 负责那些不能在捕获过程中进行的分配和加载；`docs/zh-CN/plan-schema-1.md` 列出了 plan 可能无法被捕获的所有原因）。一个 plan 在一个设备上的每次运行都使用同一个 arena，因此 **一个 plan 在多个 stream（或线程）上的运行会通过 arena 的一个 event 在设备上排序**：一次运行在自己的 stream 上等待它之前的那次运行，并在最后一次启动之后记录该 event，因此它们从不重叠，结果也正确，代价是一个接一个地运行（在该 event 最后一次记录所在的 stream 上的运行会跳过等待：始终在一个 stream 上的运行每次只花费一次 `cuEventRecord`）。必须并发的运行需要各自的 arena：`lane = tilefish.runtime.share_arena([graph], name="lane1")` 是同一个 plan 的另一个 arena（有自己的内存、锁和 event；在它的 stream 上的 `lane.run(graph, x)` 不会等待第一个 arena 上的运行），每个 stream 一个（Rust：每个 lane（通道）一次实例化）。`tilefish.capture(graph, *inputs, devscalars=..., outputs=...)` 把 plan 捕获进一个它独有的 CUDA graph：它的 `replay()` 会获取 arena 的锁，并像一次运行那样在 graph 前后等待和记录那个 event，因此 **它的回放与该 plan 的每次运行和回放都是有序的，无论来自哪个线程、在哪个 stream 上**，而 `set_devscalar` 无需同步就能为接下来的回放修改一个设备标量。在你自己的 `torch.cuda.graph(...)` 中运行的 plan 也能被捕获：等待和记录是该 graph 的外部 event 节点，因此它的 arena 就是该 plan 的 arena，它的回放与那些它能看到其记录的运行之间是有序的。但 torch 的 `replay()` 不获取锁：**当另一个线程正在运行同一个 plan 时回放一个原始 graph，会与那次运行重叠**（字节错误，没有报错），所以要么自己给两者排序，要么用 `tilefish.runtime.replay_graph(g)` 回放（它会在 `g.replay()` 前后获取 arena 的锁），要么使用 `tilefish.capture`。使用这种 graph 所持有的 arena 的第二个线程会收到一个 `TilefishOrderWarning`（配合 `warnings.simplefilter("error", tilefish.TilefishOrderWarning)` 则是一个错误）。`jit` 和 `replay` 是同一条代码路径，只是二进制文件来自两个地方，所以它们按构造就是一致的；门禁会在 GPU 上检查 plan replay、plan jit 以及相同算子的逐算子 eager 组合在每个 bucket 和 `n` 的两个取值上给出相同的字节。

**写在其输入之上的 `Out`。** 一个手写 kernel `k(x, r, y, r_out)`，如果它在写 `r_out` 的某个元素之前先读取 `r` 的同一个元素，就可以声明 `r_out: Out[Tensor[M, D, f32], MayAlias("r")]`：这样一次启动（Python 或 Rust）会接受恰好是同一个张量的 `r_out` 和 `r`，并拒绝其他任何重叠；当调用之后没有任何东西读取那个 `r` 时（一个完整的中间值，之后没有读取者，也不被返回），plan 会把 `r_out` 写在 `r` 之上，不为它单独分配缓冲区；否则结果会得到自己的缓冲区，所以两种情况下的值都相同（manifest schema（模式）3 第 5.4 节；`docs/zh-CN/plan-schema-1.md` 第 8 节）。

**拷贝步骤。** graph 中的 `r = tilefish.copy(x)` 是一个 `copy` 类型的步骤：用 `cuMemcpyDtoDAsync` 把 `x`（一个张量，或像 `x[1]` 这样的稠密视图）的稠密字节拷贝进一个独立的缓冲区，在 CUDA graph 中是一个 memcpy 节点。这份拷贝是一个原地调用可以更新的中间值，而调用方的 `x` 从不会被写入。对 `InOut` 参数的 `state[...] = r` 是一个拷贝进调用方张量的拷贝步骤。非稠密视图的拷贝则在生成 plan 时改为一次 `tilefish.contiguous` 启动（把秩为 1 到 4 的带步长的视图拷成一个稠密张量），对非稠密视图的写入也是如此：`state[...] = t.permute(1, 0)` 把转置写入调用方的张量（`docs/zh-CN/plan-schema-1.md` 第 7.5 节）。

**Memset 步骤。** graph 中的 `acc = tilefish.zeros_like(x)`（或 `zeros_like(x, dtype=i32)`）是一个 `memset` 类型的步骤：一个独立的缓冲区，其字节用 `cuMemsetD8Async` 置零（在 CUDA graph 中是一个 memset 节点），之后原地调用可以向它累加，或者由 graph 返回它（memset 直接写你的输出）。`state[...] = tilefish.zeros_like(state)` 是对你的 `InOut` 张量的一次 memset。不再需要任何 kernel 来清零缓冲区（`docs/zh-CN/plan-schema-1.md` 第 7.6 节）。

**返回视图。** graph 可以零成本地返回一个结果的 reshape（对扁平的 `y` 做 `return y.reshape(M, N)`：调用方的输出就是 `y` 的缓冲区，形状为返回的形状，写它的步骤通过一个扁平视图绑定它），也可以返回其他任何稠密视图、一个参数，或者把一个值返回两次，这些由最后一次调用之后的一个拷贝步骤放进调用方的输出。非稠密视图（转置、列块）则在那里由一次 `tilefish.contiguous` 启动来物化。

**命名输出。** `@tilefish.graph(outputs=("y", "residual"))` 给返回值命名：plan 的输出缓冲区使用这些名字（否则是 `out0`、`out1`……），`tilefish.run(..., outputs={"y": y, "residual": r})` 按名字接收它们，Rust 和 C++ host（宿主）也按名字绑定它们；三个 host 也都接受用 `out<i>` 表示第 `i` 个返回值，所以按以前的名字编写的 host 仍然可用。

**输入和权重。** `@tilefish.graph(inputs=("x",))`（或 `weights=(...)`，或两者都用）说明哪些参数每次调用都要给出，哪些由 host 在加载模型时绑定一次。plan 记录这些角色（`"roles": "declared"`），三个 host 都只绑定一次权重：`w = tilefish.runtime.bind_weights(graph, {"w1": t1, ...}, mode="replay", plan="build/", pin=p.digest)`，然后 `w.run(x)` 和 `w.capture(x, ...)`（Rust：`PlanRun::bind_weights`，一个 `WeightedRun`，它的 `launch` 和 `capture` 只接收输入）。没有这个声明时，plan 像以前一样按形状给参数打标签（不涉及任何维度时为 `weight`：完全静态的 graph 的每个参数都是如此），而 `bind_weights` 会拒绝它。

**plan set（plan 集）。** 启动次数取决于某个键的阶段，每个键对应一个 plan；`tilefish.runtime.export([g1, g2, ...], "build/")` 把它们导出为一个 *plan set*：一个 manifest（每个二进制文件只出现一次，无论哪些 plan 启动它）、每个 graph 一个 `<graph>.plan.json`，以及 `plans.json`，一个索引，它的 digest pin 住每个 plan、它们的 manifest 和每个二进制文件。replay 接受 `plan="build/"` 以及 plan set 的 digest 或单个 plan 的 digest；Rust 用 `PlanSet::load(dir, pin)` 和 `set.plan("g2")`（这些 plan 共享 manifest 及其已加载的模块）。`docs/zh-CN/plan-schema-1.md` 第 15 节说明了为什么用集合，而不是重复的步骤区间。

**plan set 中各 plan 共享的 arena。** 每次运行集合中一个 plan 的 host（一个请求的阶段 A，然后 B，然后 C）可以给它们一个 arena：`s = tilefish.runtime.share_arena([a, b, c], mode="replay", plan="build/", pin=planset.digest)`，然后 `s.run(a, x)`、`s.capture(b, ...)`、`s.bind_weights(c, {...})`。这个 arena 的字节数等于最大的那个 plan 的 arena（门禁中的 transformer block 切成三个阶段：9 109 504 字节，而不是 26 476 800 字节），每个 plan 的缓冲区在其中位于各自的偏移，因此文档及其 pin 不变，每个 plan 都在固定地址上捕获。任何一个 plan 的每次运行、捕获和回放都与其他所有运行、捕获和回放有序（一把锁，一个排序 event），所以其中任意两个都不会在设备上重叠；plan 自身区域中的任何东西都不会存活到一次运行之后，而位于 arena 中任何位置的你的张量都会被拒绝。Rust：`set.instantiate(&stream, &["a", "b", "c"])`，一个由 `PlanRun` 组成、位于同一个 `SharedArena` 上的 `SetRun`。`share_arena(..., name="lane1")` 是同一组 plan 的另一个 arena，供并发运行的 lane 使用。见 `docs/zh-CN/plan-schema-1.md` 第 15.1 节。

**Carried buffer（携带缓冲区）。** 一个阶段无需你的张量就能把中间值交给下一个阶段：在两个 graph 上都写 `@tilefish.graph(carried=("h",))`，参数 `h` 就成为 arena 持有的一个缓冲区（角色为 `carried`），位于各 plan 自身区域之后的一个区域中，对该 arena 上每个指名它的 plan 都相同。`stage_a(x, h: InOut[...])` 写它（`h[...] = encode(x)`：`encode` 的启动直接写 arena 中的 `h`），`stage_b(h)` 读它，一次运行给出除 carried 参数之外的所有参数：`s.run(stage_a, x)`，然后 `s.run(stage_b)`，后者的尺寸就是写入 `h` 时的尺寸。如果一次运行在该 arena 上还没有任何运行写过 `h` 时就读它，或者以另一种形状读它，它会在任何东西入队之前被拒绝；`tilefish.capture` 的捕获在每次回放时检查并记录 `h`。三个 host 都根据文档算出相同的布局，而文档由 pin 覆盖（`docs/zh-CN/plan-schema-1.md` 第 15.2 节）。

**调试 tap（观测点）。** `tilefish.run(graph, ..., taps={"t3": t, ("t5", 4): u})` 在某个步骤刚结束时（默认是写该缓冲区的最后一个步骤），在后面的步骤可能复用其字节之前，把 plan 的缓冲区拷贝进你的张量：这就是产品实际运行的那个 plan 的中间值，plan 及其 digest 都不变（`plan.shape_of("t3", M=64)` 给出形状；`tilefish.capture` 也接受 `taps=`；Rust：`PlanRun::launch_tapped`，以及 `PlanRun::capture_tapped`，它的回放会再次拷贝这些 tap）。

**单独运行一个步骤。** `tilefish.runtime.run_step(graph, 3, {"t2": a, "w_o": w, "t3": o}, mode="replay", plan="build/", pin=p.digest)` 在你的张量上启动 plan 的一个步骤，使用已 pin 的 plan 所指定的二进制文件和参数绑定（Rust：`PlanRun::launch_step`）：在参考实现的输入上，以产品所用的 pin，回放导出 plan 中的一个算子。

plan 启动已声明的算子、视图，以及作为融合区域的函数体算术（[`fusion.md`](fusion.md)）。`Out` 参数、对另一个 graph 的调用、对视图的原地调用，以及在其张量被原地更新之后读取的视图都会被拒绝，并给出相应的规则。`docs/zh-CN/plan-schema-1.md` 精确地规定了这个文件（每个字段、校验规则、digest），供不借助 Python 运行它的 host 使用。
