# Rust host

[English](../../guide/rust.md) | **简体中文**

`tilefish` crate（`crates/tilefish`，版本 0.0.11）是 manifest（清单）目录的 host（宿主），不需要 Python 或 Triton：它把 manifest 作为严格 JSON 读取，以与 Python 完全相同的方式重新计算各个 digest（摘要；每个 cubin 的 `sha256`、其机器码的 `sha256_code`，以及整个 manifest 的 digest），并拒绝 digest 与给定 pin（固定）不符的目录（`Pin::Digest`；`Pin::TrustDirectory` 需要显式指定）。它构建在 cudarc 的安全层之上，任何地方都不直接调用驱动：`Manifest::kernel(&ctx, ...)` 把一个 cubin 加载到一个 `CudaContext` 中，此后 kernel（核函数）会让该 context 保持存活；kernel 在 cudarc 的 `CudaStream` 上启动（`Kernel::launch`，安全：会检查 stream 是否属于 kernel 的 context），或者用 `unsafe` 的 `Kernel::launch_raw` 在原始 `CUstream` 上启动（调用期间它把 kernel 的 context 设为当前 context，结束后恢复原来的）。张量由 cudarc 的 `CudaSlice` 或其视图构成（`from_cuda`：不需要 `unsafe`；它借用该 slice，因此 slice 不会在它之下被释放，而且创建它不会在 slice 上记录任何东西），或由 host 担保的一块内存区域构成（`unsafe DevicePtr::from_raw`，有生命周期，没有追踪）。启动时把 slice 交给 cudarc 在启动所用 stream 上的 launch builder，这会把启动排在该 slice 之前的写入之后，并让 slice 自己的 stream 等待该 kernel，因此无论有多少其他 stream 读取它，释放 slice（或其 stream 上任何后续工作）都在 kernel 之后执行；从另一个 stream 写入 slice 的 kernel 会先等待 slice 自己的 stream 上已排队的所有工作，因此它在所有更早的读取者之后运行。（另一个 stream 上写入者之后的读取者由 cudarc 自己的追踪负责，这需要一个已创建了自己的 stream 的 context；启动返回 `Err` 并不保证什么都没有启动，crate 会把释放排在可能已经运行的 kernel 之后。）CUDA graph（CUDA 图）用 `launch_raw`（或 `launch`）和内存区域来 capture（捕获）：图只保存地址，不持有任何让内存保持存活的东西，因此内存释放后不得再 replay（回放）它；无论 cudarc context 如何，在正在 capture 的 stream 上启动 slice 都是一个错误，而不会得到图。加载出的函数的参数大小会与 manifest 的 ABI 比较（`cuFuncGetParamInfo`，与 Python 的 `replay` 一样），ELF 头中写的架构与其条目不同的 cubin 会被拒绝。没有 NVIDIA 驱动时 `cudarc` 会 panic，所以先用 `tilefish::driver_available()` 判断。

manifest（schema（模式）3）携带了 host 独立检查一次启动所需的信息：每个指针参数记录其声明的形状，静态轴记为大小（`["Rows", 1024]`），每个条目记录其具名维度的约束（`divisible_by`、`buckets`，以及该二进制文件为哪个 bucket（分桶）构建）。一次启动只接受它的张量。crate 由张量的大小绑定维度（带步长的视图的步长维度由其规范步长绑定；先用 kernel 读取的张量，再用 `Out` 张量绑定只有它才有的维度），并检查：维度在各参数之间以及与静态大小是否一致，bucket 是否完全匹配以及 `divisible_by`，每个张量的 dtype 和秩（设备标量是一个元素），`max_elements` 以及视图的 `max_extent`，运行时标量（由维度、由其所计数张量的元素个数或由步长推导而来）能否放进它们传递时所用的 32 或 64 位，别名，每个指针承诺的对齐（16 字节，或带步长指针的元素大小），为非带步长参数给出的张量是否连续，以及 grid 是否在设备限制之内；它还根据 grid 的表达式求出 grid。没有办法告诉一次启动某个维度是多少。更旧 schema 的 manifest 会被两个 host 都拒绝：请重新导出。

**Schema 3 与 crate。** crate 完整读取 manifest schema 3（`docs/manifest-schema-3.md`），并能启动它描述的一切：Triton kernel 和预构建的 PTX 与 cubin 二进制文件（严格按其参数，没有 scratch 槽位，`fixed` 参数在各自的槽位上），带步长的视图（`TensorRef::from_cuda_strided`，或用 `new_strided` 基于一块内存区域；任意元素步长和任意偏移），设备标量（形状为 `[]` 或 `[1]` 的张量），`i64` 步长，以及 `library` 部分中已 pin 的 cuBLASLt GEMM（通用矩阵乘；`Manifest::gemm`、`Gemm::launch`，以及用于 CUDA graph 的 `unsafe Gemm::launch_raw`）。GEMM 通过 cudarc 的 `cublaslt::result` 运行 manifest pin 的那个 64 字节算法：如果进程中的 cuBLASLt 不是选出它的那一个，如果该算法不是 cuBLASLt 本会产生的，或者如果库不认可它用于该问题，它都会被拒绝。它的 workspace（工作区）是调用方的最后一个张量（`Gemm::alloc_workspace` 按条目给出的大小分配），因此启动不分配任何内存，可以被 capture；GEMM 的 slice 与 kernel 的一样排序。crate 0.0.11 读取 manifest schema 3（并拒绝更旧的）和 plan（计划）schema 1（`tilefish.plan.v1`）。`emit` 为这一切写出类型化的启动器；crate 中提交的测试夹具都是 schema 3 的 manifest。

```python
from tilefish.hosts import rust
rust.emit(m, "launchers.rs")   # m = tilefish.runtime.export(...); ops=[...] cross-checks the declarations
rust.emit("build/", "launchers.rs", pin=m.digest)   # a directory is read only with its pin
```

`emit` 接受一个已 pin 的 manifest（`export` 返回的那个、`Manifest.load(path, pin=...)`，或带 `pin=` 的目录：它写出的文件会被编译和运行，因此没有人担保的 manifest 不会写出它，而且进入该文件的每个字段都经过校验），并写出一个 Rust 模块，每个二进制文件（每个 bucket）一个 struct，其 `launch` 接受类型化的张量（`TensorRef<'a, Bf16>`、`TensorMut<'a, F32>`：对 cudarc slice 的借用，或 host 用 `unsafe DevicePtr::from_raw` 担保的一块带长度的设备内存区域；需要的字节数超过内存大小的形状会被拒绝，在另一个 context 的 stream 上启动或使用另一个 context 的张量也会被拒绝），并为该二进制文件生成文档：它的张量、它的维度及其约束、编译进去的内容。它还嵌入生成时所用 manifest 的 digest，并拒绝其他任何 manifest；使用 `embed=True` 时，还会嵌入 manifest 和 cubin 本身。输出是确定性的。`ops=` 是可选的：其中列出的每个声明都必须与 manifest 条目所写的完全一致，并为文档提供 tilefish 签名。

逐字节一致门禁（`python/tests/rust_gate.py` 配合 `crates/tilefish/tests/gpu_gate.rs`）在 GPU 上检查 Rust host 与 `replay` 是否逐字节一致：基于一次全新的导出，分别使用 manifest 目录和嵌入的 manifest，覆盖五个 golden、在每个 bucket 上运行的分桶行 kernel、手写的 kernel（输出和原地更新的张量）、需要超过 48 KiB 动态共享内存的 `tl.dot` kernel、带步长的视图（融合的 qkv、任意元素偏移、对齐与不对齐、转置和扩展的视图、64 位步长）、设备标量、预构建的 PTX 与 cubin 二进制文件（Triton 构建产生的 PTX，以及带 `fixed` 参数的手写 PTX），以及在每个 bucket 上带和不带 bias 的已 pin cuBLASLt GEMM；它还检查 schema 3 的各种拒绝、被 capture 到 CUDA graph 中的带步长 kernel 和 GEMM，以及它们的 slice 释放相对于其他 stream 的顺序。在任何机器上，`cargo test` 和 `pytest` 都会检查：Rust 从一个已提交的 manifest 目录（`sm_103`，以及一个交叉编译的 `sm_120` 目录）算出的 digest 与 Python 算出的相同，Rust 在一千次调用上的判定与 Python 相同，并且 Rust 拒绝 Python 所拒绝的。
